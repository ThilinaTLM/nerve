# Scoped agent configuration contracts

Import from `@nervekit/contracts/agent-configuration`. Persisted schemas and pure resolution are shared with the scope service. Protocol saves/composer DTOs use these contracts directly; there is no legacy template/capability translation API.

## Pure API

- `resolveAgentConfiguration(options: ResolutionOptions): ResolutionResult` — resolves layers, per-canonical-JSON-Pointer provenance, and readiness diagnostics. Supply the existing model-catalog `clampThinking(model, level)` and `referenceAvailable(pointer, value)` to perform semantic checks; absent callbacks mean structural resolution only. Diagnostics do not replace runtime authorization. Defaults never select a fabricated model.
- `freezeChildPreferences(options: Omit<ResolutionOptions, "role" | "frozenDefaults" | "conversation">): CompleteChildSettings` — captures preferences **below requirements**. Supply creation-time `eligibleSkills`; omitted sources have no captured eligible identities. Pass the result as `frozenDefaults` on subsequent resolutions. Live preferences/recommendations are then ignored; requirements remain separate. The caller must check the final required configuration before launch.
- `projectChildSettings(settings: LeadSettingsOverrides): ChildSettingsOverrides` — validates lead defaults and removes delegation/plan presentation. Requirements and recommendations are instead rejected if incompatible with the child role.
- `canonicalSettingsEntries(settings): [pointer, value][]` — enumerates atomic/scalar merge units.
- `requirementOverlaps(recommendations?, requirements?): string[]` — conflicting recommendation pointers, including source-default coverage.
- `applySettingsMutation(current, mutation, requirements?, role?): LeadSettingsOverrides` — validates and applies sparse changes/resets without I/O. Pointers begin `/overrides`; atomic descent, required fields, unsupported paths and overlapping operations are rejected. Empty containers are pruned. Store owns revision/digest concurrency, document metadata.
- `resolveInheritedConversationSettings(options: ResolutionOptions): LeadSettingsOverrides` — resolves below conversation choices and profile requirements. Retains applicable recommendations and process layers; existing children use frozen settings and captured skill identities instead of live defaults/recommendations. Does not mutate input options.
- `normalizeSettingsOverrides(overrides: LeadSettingsOverrides, inherited: LeadSettingsOverrides): LeadSettingsOverrides` — pure value-based sparsification against resolved lower-layer settings. Compares canonical atomic units whole, prunes equal values and empty containers, and preserves source-default/named-skill semantics. Callers own requirement validation and baseline selection.
- `normalizeCreationPreferencesOverrides(overrides: CreationPreferencesOverrides, inherited: CreationPreferencesOverrides): CreationPreferencesOverrides` — removes equal default profiles and equivalent scoped-model selection sets, ignoring order and duplicates. Model selections remain atomic whole-field merge units, not element merges. An explicit empty list remains when different from inheritance.
- `configurationJSONSchemas(): Record<string, JSONSchema>` — editor schemas generated directly from Zod input contracts. Zod-only semantic refinements (including overlap and cross-field role checks) still require contract parsing.

Run `pnpm --dir packages/contracts schema:agent-configuration [output-directory]` to write editor JSON files (default: `packages/contracts/dist/json-schema/agent-configuration/`). No generated files need hand maintenance.

## Schemas

`leadSettingsOverridesSchema`, `childSettingsOverridesSchema`, `completeChildSettingsSchema`, `childLaunchOverridesSchema`, `agentPreferencesSchema`, `leadConversationAgentSchema`, `childConversationAgentSchema`, `appliedProfileSchema`, `profileDefinitionSchema`, `conversationDefaultsSchema`, `agentSummarySchema`, `conversationAgentSummariesSchema`, `configurationDiagnosticSchema`, `sha256HexSchema`, `agentMutationSchema`.

Persisted conversation loaders must select `childConversationAgentSchema` or `leadConversationAgentSchema` using trusted conversation ownership, never infer the role from editable JSON or fall back from child validation to the lead schema. The child schema and its generated editor schema require `frozenDefaults`.

Sparse parsers never insert defaults. Complete frozen settings require all non-model baseline fields, including captured skill maps/defaults. Profile label/enabled fallbacks are presentation/catalog resolution concerns, not parser defaults. A valid applied snapshot needs no catalog lookup. Consumers must treat `unsupported-reasoning` as blocking for unsupported same-layer model/reasoning pairs or incompatible required reasoning. Any non-required reasoning from a different source layer (including conversation, launch and frozen choices) is fitted to the effective model, retaining its source with `adjusted: true` and an explanatory `reasoning-adjusted` diagnostic, not an input rewrite.

## Protocol API (Phase 3)

Wire request/result schemas live in `agent-configuration-operations.ts`.

All schema names below are exported alongside the PascalCase inferred DTO types (for example `saveAgentConfigurationRequestSchema` / `SaveAgentConfigurationRequest`). The conversation channel registers:

| Operation                          | Request / result schemas                                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `agentConfiguration.get`           | `getAgentConfigurationRequestSchema` / `getAgentConfigurationResultSchema`                                      |
| `agentConfiguration.save`          | `saveAgentConfigurationRequestSchema` / `saveAgentConfigurationResultSchema`                                    |
| `agentConfiguration.getEffective`  | `getEffectiveAgentRequestSchema` / `effectiveAgentViewResultSchema` (`EffectiveAgentView`)                      |
| `conversationDefaults.get`         | `getCreationPreferencesRequestSchema` / `getCreationPreferencesResultSchema`                                    |
| `conversationDefaults.save`        | `saveCreationPreferencesRequestSchema` / `saveCreationPreferencesResultSchema`                                  |
| `conversation.previewAgentProfile` | `previewProfileTransitionRequestSchema` / `previewProfileTransitionResultSchema`                                |
| `conversation.setAgentProfile`     | `setConversationAgentProfileRequestSchema` / `profileTransitionResultSchema`                                    |
| `interaction.resolve`              | existing envelope, new `PlanReviewResolution` and `interactionResolveResultSchema` (`InteractionResolveResult`) |

Agent save requests are flat `{scope, expectedRevision, expectedDigest, changes, resets}`. `AgentScope` is `{scope:"user"}`, `{scope:"project",projectId}`, or `{scope:"conversation",conversationId}`. `PreferenceScope` excludes conversations. Changes are sparse; resets are canonical `/overrides/...` pointers. Validation rejects atomic descent, unsupported paths, metadata edits and overlapping operations. Required-field and trusted child-role checks still belong to the service. No parser inserts defaults or writes inherited settings. Creation saves use the same CAS fields, but changes contain only `defaultAgentProfile` and atomic `scopedModels`; their two whole-field reset paths are the only allowed resets. The existing `capabilities.*` / `harnessSettings.*` channel operations are removed, not forwarded. `conversation.configure` edits only system prompt, instructions and working directory; it cannot write agent choices.

Save behavior is value-based: after validating/applying the mutation, normalize the entire resulting override document against the resolved layers below the edited scope, then persist and return sparse overrides. This also cleans pre-existing redundant values on the next save; normalization does not rewrite untouched documents or change requirements/profile contributions. Do not compare against a resolution containing the edited scope or overlaid requirements. Conversation baselines include applicable recommendations; existing children use their frozen baseline, never current parent preferences. Required-field checks remain authoritative and must run before normalization. UI override indicators should follow the returned sparse document, not merely whether an explicit value was submitted. Available `agentConfiguration.get` responses require `inherited: LeadSettingsOverrides`: the authoritative resolved baseline below the requested scope, excluding that scope's overrides and requirements. Available project-agent-defaults/draft responses require the same `inherited` field below supplied draft overrides, excluding requirements. Available `conversationDefaults.get` responses require `inherited` in the creation-overrides shape (`defaultAgentProfile?`, `scopedModels?`), resolved below the requested scope. These baselines may be empty but cannot be omitted; clients use them for normalization rather than reconstructing inaccessible process layers or subtracting requirements from effective settings. Save results and effective-agent DTOs do not add this field.

Skill defaults compete with lower named decisions: a local `defaults.file=false` can remain meaningful even when the inherited default is also false, because it masks an inherited named `true`. Equal source defaults are removed only when doing so preserves inherited named behavior not explicitly overridden locally. Named values compare against a retained local source default first, otherwise against the inherited named value/source default. Thus a named value equal to its inherited named decision can still be necessary beneath a changed local default. The helper does not flatten defaults into named decisions or expand eligibility, preserving frozen-child boundaries.

Get/save results use `available`/`saved`, or `conflict`/`unavailable`/`invalid` as applicable. `ConfigurationMutationFailure` carries redacted scoped diagnostics. Conflict's optional `current: ConfigurationVersion` is omitted when a trustworthy current revision/digest is unavailable; never invent it. A missing optional source uses revision 0 and digest `"missing"`. `ConfigurationDocumentSource` contains scope/path/generation/revision/digest only: project internal generation documents to metadata rather than sending executable source documents as another client authority. Health errors do not silently become empty overrides.

`EffectiveAgentView` is `available` (conversationId, trusted role, appliedProfile snapshot or null, resolution, scoped diagnostics, source metadata) or `unavailable` (conversationId, diagnostics). `agentResolutionSchema`, `fieldProvenanceSchema`, `configurationSourceSchema`, and `resolutionDiagnosticSchema` validate the pure resolver's existing values, not a separately maintained DTO. Recommendation/requirement provenance names its controlling profile. Model absence remains absence plus `model-required`; no fabricated model/reasoning/permission is supplied by an unavailable response. Creation gets expose that scope's sparse overrides and resolved creation preferences, where Coding is the built-in start profile. The composer uses `getEffective`, not old materialized config agent fields. `conversation.create` accepts context-only `config`, optional sparse `overrides`, and optional digest-bound `agentProfile: ProfileTarget`; omitted selections use normal resolution. Prospective `conversation.previewSystemPrompt` uses projectId/overrides/optional target profile/context and returns available prompt plus resolution, or unavailable diagnostics.

`agentConfiguration.changed` and `conversationDefaults.changed` are global ephemeral invalidation hints carrying only the affected typed scope. They replace capability-change notices; consumers refresh loaded views only. Correctness still relies on acknowledged service publication and generation guards, not event delivery or scans of unopened conversations.

### Profile and plan confirmation

`ProfileTarget` is `{name,digest}`: stable current-project catalog name and exact definition-byte digest, never a caller-selected source namespace. `ProfileTransitionPreview` includes that target, display source, expected revision/digest, recommendations/requirements and hypothetical resolution. Preview never applies anything. Normal explicit switch uses `action:"switch"`; Apply updated profile uses `action:"reapply"` and the same applied name (validated by the runtime). Both require target bytes and CAS tokens, with no transition ID or journal. They replace only the captured profile contribution, preserving conversation choices; arbitrary overrides/choices are not accepted by this command.

`PlanReviewRequest` captures `targetProfile`, expectedRevision/expectedDigest and the existing plan asset/path/content metadata. Approval is `{kind:"plan_review",decision:"approve",confirmation:ProfileConfirmation,feedback?}`; existing optional review feedback is preserved. Confirmation carries the captured target, expectedRevision/expectedDigest, transitionId and optional sparse `choices: ImplementationChoices` (`model` and `reasoningLevel` only). Omitted choice fields remain untouched; a supplied model is atomic. Rejection is `{kind:"plan_review",decision:"reject",feedback?}`. The old implementationModel/implementationThinkingLevel fields are not accepted.

`ProfileTransitionResult` is `applied` (committed source, effective view), `refresh_required`, or configuration `unavailable`. `ProfileRefreshRequired` has reason `target_changed`, `target_unavailable`, `target_untrusted`, `requirement_conflict`, or `configuration_changed`, diagnostics and an optional refreshed preview. A missing/untrusted target must not be replaced automatically; omit the preview when no valid target can be offered. Map stale/invalid confirmation to this result, not an irreversible failed review. Only newly submitted choices conflicting with requirements are rejected; existing choices may remain underneath temporary requirements. Persistence/publication failure leaves the pending review intact. Runtime owns serialization, trust/applicability/requirement validation and ordinary revision/digest CAS publication of `agent.json`, the sole active-profile authority. Manual saves never append conversation events; lost responses require reloading current configuration and stale retries require refresh. The optional historical `lastTransition` field is readable but inert, and omitted on ordinary document rewrites.

Plan approval persists the normal review decision, saves the profile, then atomically settles the tool and accepts one deterministic-ID user input through the existing queue. That visible message starts `Implement the approved plan.` and contains the immutable reviewed title/content and feedback; the tool result records only approval. Queue delivery precedes the next freshly captured model request. Rejection preserves the pause gate and submits no implementation input. Settled retries acknowledge the recorded decision without reading or changing current configuration. An interrupted pending accepted approval always refreshes/reopens for explicit reconfirmation—even when current configuration matches the requested target and choices. It never automatically reapplies, settles, or queues implementation; unavailable configuration remains blocked until reload. The required plan confirmation `transitionId` is approval correlation only, not a profile receipt. No schema performs these side effects.

Ordinary interaction resolutions return `{status:"resolved"}`. Initial profile/plan approval returns the transition result (including refresh_required); settled interaction retries return the recorded `{status:"resolved"}` acknowledgement; the channel no longer flattens it to null. No compatibility translation or legacy Set/Lock DTO is added.
