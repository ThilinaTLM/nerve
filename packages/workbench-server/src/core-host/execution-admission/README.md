# Final execution admission

`createExecutionAdmission(source)` implements `PermissionPort.prepareAdmission`. Loading is asynchronous; each `check()` reads **current** validated policy memory and evaluates it synchronously. Invalid policy returns configuration-blocked diagnostics. Authority binds exact policy/trust and hard-role restrictions; process-local generations are evidence, not durable approval authority. `createPermissionPort(home, storage, source)` requires the scoped source and exposes no legacy evaluator or harness fallback.

`createConversationCore` composes the real scoped permission source, agent service, prepared tool host and core admission gate. Its optional process-host dependency replaces external process execution, not preparation or authorization. Production-wiring unit tests use temporary homes, actual JSON documents/repositories, explicit publication/invalidation, and the real prepared host dispatch. They cover live policy changes, stale approval denial, malformed/unreadable documents, Retry/Cancel, child restrictions and restart target changes. No database schema changes are involved.

## Preparation and dispatch

Prepare credentials, canonical arguments, working directory, interpreter/shell and dispatcher context before admission. Bind account identity and non-secret configuration, never credentials. A supplied request capture is conversation-bound; missing IDs after restart recapture current configuration. Missing/revoked credentials never select another account.

Bash preparation resolves the complete shell/project-manager invocation and snapshots its environment before admission. Its non-secret target includes the actual shell/launcher, manager/config-file selection, project-environment mode and cwd. Ambient environment values can contain secrets: they remain only in the transient prepared invocation, never in approval JSON or its target digest. `CoreProcessHost` consumes that invocation directly after asynchronous output-directory creation; it does not rediscover shell, project environment or cwd. Command/cwd mismatches fail. Project scripts, shell startup files and programs subsequently executed by the admitted command remain ordinary executable input, not configuration re-selection by the host.

Agent `launch start/restart` prepare their selected definition/run and complete shell invocation before admission. Standalone restart loads its source/environment once during preparation. The service, definition-start arbitration, restart cancellation, workbench process adapter and supervisor carry the exact transient `preparedShell` to spawn; none reloads shell settings, environment or project-manager selection on the admitted path. Command/cwd mismatches fail before dispatch. Only explicit launch env overrides retain their existing storage semantics; the prepared invocation and ambient environment are never persisted. Explicit user launch APIs remain available and outside tool admission.

Production launch tests exercise the real LLM-request/capture path, permission source, launch service, catalogs, repositories and process adapters, replacing only external LLM/native processes. They compare the granted target digest with the spawned invocation, change shell/environment/project-manager inputs after admission, verify definition and standalone restarts, and require fresh approval for changed command/cwd or restart-recaptured shell targets.

The core checks policy after all asynchronous preparation and again after synchronous state-publication callbacks, immediately before dispatch. It fences concurrent workers, independently rejects child-restricted tools, and tests grants only after current policy evaluation. Approval persists the binding actually presented. Resolved approval interactions survive `running`, restart readmission and settlement. Health recovery retries admission, never approval. Started non-replay-safe calls keep indeterminate recovery handling.

## Harness authority audit

- Removed the unused harness-dependent permission evaluator and the unwired legacy profile/harness runtime readers (`agent-profile-policy`, `conversation-harness.service`).
- Current permission selection comes from scoped `agent.json`; policy definitions/overlays/trust come from the scoped permission source. Current LLM advertisement uses `scoped-turn-resources` and scoped profile/resource resolution, not harness settings.
- Remaining harness readers are legacy settings/health projections (`home-configuration`, `project-configuration`), storage path declarations, and frozen migration converters. Legacy capability/profile-availability metadata still uses settings projections for display APIs; it does not authorize, launch scoped children, or advertise tools in current LLM requests. Those readers must not be reintroduced into admission or executor selection.
- `ImplementationChoices` is a strict model/reasoning-only schema. Profile transitions parse it at the runtime boundary, reject conflicting requirements with `refresh_required`, and preserve permission authority solely from existing explicit overrides and the target's requirements; approval cannot submit permission/tool overrides.
