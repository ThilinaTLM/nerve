Sub-agent profiles: one model, four layers

A redesign proposal for creating, customizing and overriding sub-agent profiles across Built-in, User, Project and Conversation layers. The goal: simple for the common case (“use a cheaper model for Explore in this chat”), and flexible for the deep case (“create a team-shared Reviewer with its own instructions, tools and permissions”). All screens are mock data. No application code is involved.

What is hard today

Inheritance is shown as raw data

  • Editor has a separate “Scope overrides” list with a Pin and Reset button for each of ten fields, far from the field it describes.
  • Popover shows explore · builtin, Model: lead · builtin, Inherited: enabled true, model lead….
  • “Inherited” badge does not say from where, or what was changed.

Actions are ambiguous

  • Five unlabeled icons per row (edit, power, download, duplicate, reset). Download really means “copy into this scope”.
  • Enable/disable is a power icon and an “Enabled” badge, not a switch.
  • “Reset” means different things: remove override, restore built-in, delete a profile.

Conversation view is too heavy

  • Three paragraphs of explanation before the first profile. The Tools and Skills tabs are one-line rows; Sub-agents is a long form.
  • Each profile expands to a model picker, thinking select and three Reset buttons, all visible at once.
  • There is no way to keep a conversation tweak as a project default.

Design principles

  1. One profile, many layers. A profile has one name. Built-in, user and project layers either create it or customize it. They never make a second copy with the same name.
  2. Inheritance shown on the field. Each field says where its value comes from (“From Built-in”) and has a Revert link on the field itself. There is no separate inheritance panel to cross-reference.
  3. The page tells you which layer you are editing. Its header says which layer receives your edits and which file holds them. No edit can reach another layer by accident.
  1. The right depth at each layer. Conversation: switches and a model/thinking quick-edit. Settings: the full editor. The popover links to Settings for anything deeper.
  2. Safe defaults when you create. New profiles start read-only and use the lead’s model, thinking, tools and skills. The description is required because the lead uses it to choose a profile.
  3. Every change can be reversed. Revert field, Reset customizations and Delete profile are separate actions with separate wording. Built-in profiles can be disabled, but never deleted.

The layer model

Resolution goes bottom-up: each layer sets only the fields it changes, and the nearest layer wins. This is the current server model (sparse entries, origins, pin/reset, trust). The redesign changes how it is presented, not how it is stored.

  1. Layer line under the title. Names the layer, its reach and its file. It replaces “Saved in user config/subagents.json” in the dialog description.
  2. Grouped by origin. “Your profiles” first, then “Built-in”. A customized built-in stays in Built-in with a Customized marker. Hover shows which fields changed, e.g. “model, thinking”.
  3. Switch on each row replaces the power icon and the “Enabled” badge. A disabled profile is dimmed but stays in place, so rows do not jump.
  4. Summary line uses plain words: model · thinking · permission · differences from the lead (“+Jira”, “2 skills”). Shown only where it differs from the lead.
  5. ⋯ menu shows only the actions that apply to that row. Built-ins never offer Delete. Reset customizations appears only when this layer has changes. It names them and asks for confirmation.
  6. New profile starts with a choice: Blank, Copy of an existing profile, or a template. The full editor then opens. A blank profile is safe by default (read-only, same as lead).
  7. Problems appear on the affected row with a fix action (“Choose model”). One summary sits above the list. Technical JSON stays in a collapsed section.
  8. The filter box appears only once there are more than 6 profiles. It is shown here for illustration.

  1. Same page, different layer. The green Project mark and the repo file path make it obvious that edits are shared with the team.
  2. Three groups: “Project profiles” (created here), “From User”, “Built-in”. Customized rows show Customized here, plus a small mark if User also changed them.
  3. Trust uses plain language. One banner explains what is ignored right now and why. Review… shows each entry, flags risky fields (Autonomous, instructions, extra tools) and approves this exact version. Any later edit to the file asks again.
  4. Editing a project profile in Nerve trusts only your own edit. The banner stays until the whole file has been reviewed, as today, but now says so in one sentence.
  5. Reset customizations shows before/after values and where each restored value comes from. It warns that the file is shared, and the notification offers Undo.
  6. Empty state explains that inherited profiles are listed above and offers to create one.
  7. Delegation in a project shows its origin (“From User”). Changing it adds a Revert link, the same pattern as profile fields.

  1. Full page instead of a dialog. Breadcrumb back to the list. Unsaved changes are checked on navigation. The page has a URL, so it can be opened from the conversation popover.
  2. Header: label, origin badge, the B/U/P strip (filled = that layer sets values, ring = layer being edited) and the profile’s on/off switch.
  3. Provenance on the field replaces the old “Scope overrides” list. Inherited fields are dashed and say “From User”. Changed fields say “Changed here · Revert”, and the help line names the value Revert restores.
  4. Pin is rare, so it lives in the field’s ⋯ menu as “Keep this value here”.
  5. Instructions are read-only when inherited. Customize copies the text so you can edit it, and warns that later Built-in updates won’t reach the copy.
  6. Tools use a tri-state per tool (Same as lead / On / Off) with a live “→ on/off” result. Changed rows are tinted. Tools with settings get a settings… link for a per-profile override.
  7. “Same as lead” shows the current resolved value (“now Claude Opus 4.5”). Thinking levels the chosen model can’t use are disabled before you save.
  8. Creating: the name is derived from the label, can be edited, and is locked after creation. A name clash links to the existing profile (“Edit Reviewer”, or “Customize Explore instead” for a built-in), because a profile with the same name in this layer would customize that profile, not create a new one. The description is required and has a counter, because the lead chooses profiles by it.
  9. Explicit Save for this form (multi-field validation, shared file), with a count of changes and the target file. Optimistic concurrency shows a non-destructive conflict banner.

  1. Rows match the Tools tab: name, a one-line summary, switch and chevron. The tab count (3/4) means available / total, as in the other tabs.
  2. Orange dot = changed in this conversation. The header reset icon clears all conversation changes. The origin of other values appears only in quick edit, where it matters.
  3. Explanations shrink to one footer line (“Applies to new sub-agents”). Running children are mentioned in quick edit for the profile that has them.
  4. Quick edit covers the three fields people change mid-task: on/off, model, thinking. Each field shows its origin and Revert. Everything else is a read-only summary, with Full editor ↗ opening the profile’s Settings page.
  5. Model picker lists “Same as lead” and the inherited default with their current values, then models recently used for sub-agents. Unauthenticated providers show “sign in”.
  6. Save as default… writes the conversation’s changes to Project or User, removes them from the conversation, and offers Undo. It turns a temporary tweak into a lasting setting without opening Settings.
  7. Delegation off keeps rows visible but dimmed, so you can still prepare profiles before turning it on.
  8. Unavailable profiles stay listed with a disabled switch and the reason, plus a link to the fix. They never just disappear.
  9. Conversations can’t create profiles. That needs a name, description and instructions, which belong to a layer you can share and reuse.
