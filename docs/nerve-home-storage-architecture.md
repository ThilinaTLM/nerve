# Nerve home and project storage architecture

> **Status:** Proposed architecture for discussion. This document describes the desired storage boundaries and formats; it is not an implementation plan.

## Goals

Nerve storage should make it obvious which content is:

- human-readable and portable configuration;
- sensitive authentication or machine identity;
- authoritative application data owned by Nerve;
- user-authored harness resources;
- transient or rebuildable state.

Configuration that users may review, back up, or transfer uses versioned JSON files. Relational and historical state that users should not edit manually remains in SQLite. Secret values never appear in plaintext configuration.

Unless explicitly overridden by `NERVE_HOME`, the user-level root is `~/.nerve`.

## User-level layout

```text
~/.nerve/
├── manifest.json                    # Nerve-home format and version
├── daemon.json                      # Active daemon discovery metadata
│
├── config/                          # Human-readable portable configuration
│   ├── daemon.json
│   ├── harness.json
│   ├── ui.json
│   ├── permissions.json
│   ├── providers.json
│   └── integrations.json
│
├── secrets/                         # Sensitive; restricted permissions
│   ├── master.key
│   ├── credentials.enc
│   └── daemon-token
│
├── data/                            # Authoritative Nerve-owned data
│   ├── nerve.sqlite
│   ├── payloads/                    # Nerve-created tool-call output dumps
│   ├── reports/                     # Reports generated by agents
│   ├── images/                      # Durable pasted/imported images
│   └── plans/                       # Plan-mode plan files
│
├── tasks/                           # File-backed task logs
│   └── <task-id>.logs.jsonl
│
├── agent/                           # User-authored harness resources
│   ├── AGENTS.md
│   ├── SYSTEM.md
│   ├── APPEND_SYSTEM.md
│   ├── skills/
│   └── suggestions/
│
├── tls/                             # Machine-specific TLS identity
│   ├── nerve-local-ca-key.pem
│   ├── nerve-local-ca.pem
│   ├── nerve-local-ca-public-key.pem
│   ├── lan-server-key.pem
│   └── lan-server-cert.pem
│
├── tmp/                             # Disposable in-progress execution files
├── cache/                           # Fully rebuildable
├── logs/
├── crashes/
├── migrations/
└── backups/
```

There is no general-purpose `artifacts/` or `runtime/` directory.

Nerve also discovers user-level skills from the shared agent ecosystem location outside `NERVE_HOME`:

```text
~/.agents/
└── skills/
```

Both `<NERVE_HOME>/agent/skills/` and `~/.agents/skills/` are supported user-level skill sources.

## Home manifest

`manifest.json` replaces the current `VERSION` marker. It identifies the Nerve-home layout before any other file is opened.

```ts
interface NerveHomeManifest {
  format: "nerve-home";
  version: 1;
}
```

```json
{
  "format": "nerve-home",
  "version": 1
}
```

The manifest contains no mutable application settings.

## Storage boundaries

### Human-readable configuration

`config/` contains user-level settings that users may inspect, edit, export, and transfer. Every file has a top-level version and is validated against a contract in `packages/contracts`.

Nerve writes configuration atomically and uses deterministic JSON formatting. Command-line arguments and environment variables can override saved values without rewriting the files.

### SQLite

`data/nerve.sqlite` is authoritative for relational, historical, transactional, or internal state, including:

- registered projects;
- conversations, messages, agents, and run state;
- tool-call history and lifecycle records;
- task metadata and execution state;
- durable protocol events;
- conversation-specific model, mode, and permission selections;
- ownership, integrity, and lifecycle metadata for file-backed data;
- indexes and relationships requiring transactions.

SQLite sidecars such as `data/nerve.sqlite-wal` and `data/nerve.sqlite-shm` may exist while the database is open. They are implementation-managed parts of the database lifecycle.

### Tool-call payloads

`data/payloads/` contains dumps created by Nerve on behalf of a tool call, not arbitrary files created through `write` or `edit`.

A suitable owner-scoped layout is:

```text
data/payloads/
└── conversations/
    └── <conversation-id>/
        └── tool-calls/
            └── <tool-call-id>/
                ├── result.json
                └── files/
```

Examples include:

- complete serialized tool results that are too large to inline;
- fetched web response bodies;
- raw Jira or Confluence response dumps;
- downloaded integration attachments;
- files collected from a tool-owned output directory such as Python output.

SQLite stores the stable owner IDs, digest, size, media type, and logical reference. A filesystem path is not the identity of a payload.

### Agent-authored files

Files intentionally written by an agent through `write` or `edit` are not payload dumps. They are written to the absolute path supplied to the harness for their explicit category or user-selected destination.

Known Nerve-owned categories include:

| Directory       | Purpose                                                       |
| --------------- | ------------------------------------------------------------- |
| `data/plans/`   | Plan-mode documents written and edited by the planning agent. |
| `data/reports/` | Reports authored by agents, including Explore reports.        |
| `data/images/`  | Durable pasted or imported images made available to agents.   |

Nerve stores logical references for these files where records need to survive a home move. At execution time, the host resolves a logical reference against the active `NERVE_HOME` and provides the harness with an absolute path. Agents therefore always receive usable absolute paths without making persisted records dependent on the old home location.

### Task logs

Task metadata remains authoritative in SQLite. File-backed task output uses one JSONL file per task without a redundant task directory:

```text
<NERVE_HOME>/tasks/<task-id>.logs.jsonl
```

Any structured task lifecycle fields belong in SQLite rather than alongside the log.

### Suggestions and harness resources

User-level suggestions are loaded from:

```text
<NERVE_HOME>/agent/suggestions/
```

Project-level suggestions are loaded from:

```text
<project>/.nerve/suggestions/
```

Suggestion source files are user/project-authored. Internal enablement and trust decisions may remain in SQLite because they are Nerve-owned records tied to evaluated files and hashes.

### Temporary files

`tmp/` is only for disposable, in-progress execution material. A successful result that must remain accessible is promoted into its explicit durable category before the tool call completes:

- Nerve-created dump or downloaded output → `data/payloads/`;
- plan → `data/plans/`;
- agent report → `data/reports/`;
- pasted/imported image → `data/images/`;
- task process output → `tasks/<task-id>.logs.jsonl`.

Temporary files are not part of backup or export guarantees.

### Secrets

`secrets/` contains encrypted provider and integration credentials plus restricted machine-local authentication material.

- `master.key` protects `credentials.enc`.
- `credentials.enc` contains API keys, OAuth credentials, and integration tokens.
- `daemon-token` authenticates local HTTP and WebSocket clients and is not portable user configuration.

Human-readable provider and integration files contain only metadata and secret references. Secret values must not appear in configuration, project `.nerve/` directories, ordinary exports, logs, or SQLite records intended for inspection.

Copying `master.key` and `credentials.enc` together supports whole-home recovery. Portable credential export should instead re-encrypt selected credentials with an export passphrase. Environment-provided credentials remain external and are not persisted by Nerve.

### Daemon discovery, locks, and TLS

The root `daemon.json` is transient discovery metadata for the currently active daemon: daemon ID, PID, URL, ports, version, and start time. It is removed during clean shutdown and ignored when stale. It is distinct from `config/daemon.json`.

Migration coordination remains under `migrations/`. The startup lock may remain a sibling such as `<NERVE_HOME>.startup-lock.json` because it must be acquired before Nerve knows which internal home layout is present.

`tls/` contains generated private keys and certificates for the local installation. It is machine identity, not portable application configuration. Private keys use restrictive permissions.

### Cache, diagnostics, migrations, and backups

- `cache/` is fully rebuildable and may be deleted without losing authoritative state.
- `logs/` and `crashes/` are retained diagnostics and may contain sensitive user or project content.
- `migrations/` contains the migration ledger, rollback work, archives, and migration locks.
- `backups/` contains retained Nerve-managed snapshots or preserved pre-migration homes and must not be treated as cache.

### Legacy v2 migration

Normal startup remains manifest-first and fails closed for unmanifested homes. The only import exception is an explicit, offline migration from the immediately preceding `{ "format": "nerve-workbench-state", "version": 2 }` home. The released source boundary is Nerve 0.26 with the immutable storage ledger ending at `0012-remove-workers`; it migrates directly to `nerve-home` v1 and does not need to run `0013-canonical-storage` first. Canonical-v3 v2 homes created by later development builds remain accepted as a compatibility source. Desktop requires confirmation; remote mode never inspects local storage.

Migration builds and validates a fresh v1 home in a sibling staging directory before renaming anything. For a released post-0012 source, the importer reads its JSON, JSONL, encrypted-secret, and managed-file formats without rewriting them and emits the current v1 schema directly. It imports the six configuration documents, recognized encrypted provider/tool credentials, projects and agents needed by conversation history, canonical conversation records and durable events, referenced payloads, and user-authored plans. It rewrites managed-file references to logical v1 paths and records file metadata in SQLite.

Logs, crashes, caches, temporary files, task process state/logs, daemon discovery, TLS identity, and other generated runtime state are not imported into the live home. Project allow permissions require new digest-bound approval. The complete source home is retained under `backups/` after successful promotion. A sibling journal and lock make interrupted rename phases recoverable; unknown, malformed, newer, or actively written homes remain untouched.

## Project-level layout

```text
<project>/
├── AGENTS.md                        # Project/ancestor context instructions
├── .agents/
│   └── skills/                     # Shared agent ecosystem skills
└── .nerve/
    ├── config/
    │   ├── harness.json
    │   ├── permissions.json
    │   ├── ui.json
    │   └── providers.json
    ├── SYSTEM.md
    ├── APPEND_SYSTEM.md
    ├── skills/                     # Nerve-specific project skills
    ├── tasks/
    │   └── definitions.json        # Portable saved task definitions
    └── suggestions/
```

Nerve supports context from project and ancestor `AGENTS.md` files. It discovers project skills from `.nerve/skills/` and applicable project/ancestor `.agents/skills/` directories.

Project configuration contains only project-portable values. Credentials, daemon settings, runtime state, conversation history, and machine identity never belong in a project directory. Project provider definitions may reference user-owned credential names but cannot contain credential values.

Every file inside `<project>/.nerve/` derives its project scope from its enclosing project directory. It must not persist, require, compare, or trust a Nerve `projectId`, because project IDs belong to one local installation. Storage boundaries inject the active local project ID when constructing runtime or API objects and remove it before writing project-resident files. Project-scoped relational and runtime state under `NERVE_HOME` remains ID-based because it is installation-owned rather than repository-portable.

### Project permission safety

Project configuration is repository-controlled input and cannot silently grant itself authority merely because a repository was cloned or opened.

Nerve distinguishes:

- project-requested rules from `<project>/.nerve/config/permissions.json`;
- user-owned rules from `<NERVE_HOME>/config/permissions.json`;
- hard application constraints that neither source can override.

Project deny rules may take effect directly. Project allow rules require an explicit trust decision or user approval before they expand authority. User denies and hard constraints always win.

## Configuration precedence

For settings valid at both user and project scope:

1. command-line arguments;
2. environment variables;
3. project `<project>/.nerve/config/*.json`;
4. user `<NERVE_HOME>/config/*.json`;
5. product defaults.

Daemon configuration, user identity, and secrets are not project-overridable. Permission evaluation uses security composition rather than simple last-writer-wins precedence.

## Electron browser profile

Electron's active Chromium `userData` profile remains outside `NERVE_HOME` in Electron's operating-system application data location. Nerve currently relies on this Electron default rather than redirecting `userData` into `NERVE_HOME`. Typical locations are the platform application-support/configuration directory, such as `~/.config/<app>` on Linux, `~/Library/Application Support/<app>` on macOS, and `%APPDATA%\<app>` on Windows; the exact directory is determined by Electron and the packaged application identity.

Keeping it separate makes whole-home backup and migration safe while Chromium has cookies, IndexedDB, cache, local storage, and singleton files open. It also keeps client/device state separate from daemon-owned portable state. Portable UI preferences belong in `config/ui.json`; browser session state is intentionally device-local and excluded from Nerve-home migration. Explicit profile-path overrides may still be used when development or deployment isolation is required, but they should also remain outside `NERVE_HOME`.

## Export and portability

A normal configuration export may include:

```text
nerve-config-export/
├── manifest.json
├── config/
└── agent/
```

An optional credential export adds a passphrase-encrypted secret bundle. Daemon discovery state, daemon token, TLS identity, caches, temporary files, logs, crashes, and Electron browser state are excluded by default.

Project configuration is already portable with the project and is not duplicated into a user-level export.
