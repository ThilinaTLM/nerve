# Settings UI patterns

Design rules for settings pages in `packages/workbench-app`. `settings-typography.test.ts` enforces the heading rules.

**Page primitives.** The generic layout pieces live in `@nervekit/ui-kit/components/composites/page` so extension pages can look like settings pages: `PageHeader`, `PageSection` (`divided`, `surface`), `FieldRow` (with `SelectField` as its control for choices), `ToggleRow`, `PageList` + `PageItem`, `PageEmptyState`, `PageStatGrid`. They know nothing about layers or origins. Rows read the section's `data-page-surface` / `data-page-divided` attributes, and the divided two-column row layout reacts to an ancestor `@container/page` (the settings shell declares it). `SettingsSection` (section anchor id, info hint, layer labels, split labels) and `SettingsSelectRow` wrap them; everything else on this page is app-only. The rest of this page names the primitives by their ui-kit names.

## Headings

Settings has three heading levels:

- Page title: `text-title` medium foreground (`PageHeader`, `pb-2` of space below).
- Section heading: `text-ui` medium foreground, optionally followed by ONE `text-caption` muted description line.
- Entity title (`EntityCard`, e.g. a profile): `text-ui` regular foreground.

Row titles are `text-ui` regular foreground and all supporting text is `text-caption` muted, so weight and colour carry the hierarchy. Headings are sentence case, never uppercase eyebrows. Longer detail goes in a `SettingsInfoHint` tooltip, not a paragraph. Use `SettingsSection` for every group of rows; an entity such as a profile gets an `EntityCard`, never a muted group heading above it.

## Copy: say it once

Every page has a title and ONE short sentence under it (the registry `description`, or the item's own for a detail page): plain words, no repeat of the title, no mechanics that a section or tooltip already carries. Say each thing once, at the highest level it holds for: the page description covers its sections, a section description only adds what the heading does not say, and a row never restates its section. An empty state inside a titled section is one short line ("Not found.", "None.") with its action if there is one, never a title plus a description that repeats the section. Longer detail goes in a `SettingsInfoHint` tooltip.

## Navigation

`SettingsNav` takes `SettingsNavGroup[]` (optional `GroupLabel` caption: `text-caption text-muted-foreground`, no hover or icon; items `text-ui` with a lucide icon, muted until active). Never reuse a group title as an item name. The active item is `bg-selected`, a persistent state that should not depend on the quiet fills. The sidebar has no right padding: the nav pads its own content so the thin scrollbar sits flush with the panel's edge. Groups never collapse (collapsing hides destinations).

### One tab, and what needs you

Settings is one tab kind. The open project is the active workspace project: it adds a column on layered pages (General and Tools only on request, see below); without one the surface is User only. There is no project-only group: every project item is decided on the page where it is used. Opening a project's settings (`openProjectSettingsPane`) selects that project and opens or focuses the settings tab; a tab restored from the old per-project kind becomes the settings tab. A nav row shows a count of its page's items that need the user (waiting for review, or not working; User and project together, read from `configuration.attention`; warnings never count) as a `SettingsNavBadge` (`warning`, a 16px solid circle). A project's `agent.json` counts once, on General; the project's `prompt-suggestions.json` counts on Suggestions. The gear opens the same tab. Items waiting for review reach the user through the bell island and the transcript marker, whose **Review** opens the review dialog; **Details** there opens the item on the page that holds it. The project's conversation welcome adds one line while project items wait ("3 project files need your review · Review", opening the first item); declined items never count, and the line is hidden on the phone.

## Layers and origin groups

The unified settings surface has two layers: **User** (every project) and the open project, always labelled "Project" (never its name: names can be long or odd). Visible labels, group captions, badges, menu items, callouts and aria-labels say "Project", "this project" or "Project only"; only a tooltip may name the project once, where it adds clarity. An absent value inherits; nothing shows a "follows" state except tooltips. Primitives live in `$lib/presentation/settings`:

- **`OriginGroup`:** a list group with a caption (origin icon, name, count). Order groups Project (`briefcase-business`), User (`circle-user`), other sources (Agent Browser `globe`, extensions `blocks`), Built-in (`package`). The origin explanation is a hover tooltip on the caption, never an ⓘ icon. An empty group is hidden unless `emptyText` is given, which is for groups the user can add to (with the add action). With a project open and `layers` on, the column labels sit at the right of the caption line; a project-only group shows none, because its caption names the project, and an empty group shows none.
- **`ColumnLabels` / `SplitColumns`:** "User" and "Project" as quiet, text-only captions (no icon, border, background, divider or header row inside the card), each with a hover tooltip. They sit on the line directly above the card: the group caption line for `OriginGroup`s, the description line of a section (`SettingsSection` `layerLabels`; a short right-aligned line of their own when the section has header actions), the heading line of a heading-only block, or a short line of their own (`LayerEnabledTable`). Never render them inside a card. A project-defined block (a project extension's page) hides the User label but keeps its width. Without a project there are no labels at all.
- **Trust decisions:** every user and project item that changes what agents do (profiles, skills, rule sets, permission files, `agent.json`, suggestions, extensions, MCP entries) has one of three states, shown by `TrustStateBadge` (Needs review `warning`, Trusted `success`, Declined `neutral`), and the same actions from `TrustDecisionActions`: Needs review → **Decline** · **Trust**; Trusted → **Revoke** (it becomes Declined); Declined → **Trust** only (no "ask again"). On a page, **Trust** opens the [review dialog](#review-dialog) as confirmation; Decline and Revoke decide on the content the page read. A waiting item gets a warning problem line ("Waiting for your review") with **Review**, which opens the review dialog; a declined one only a quiet Declined badge (its tooltip says "changed since you declined" where the page knows), never a problem line. An item's page opens with `ConfigurationReviewCallout` ("Waiting for your review", or "You declined it") and shows the dialog's **What it can do** and **Source** sections (`ConfigurationReviewSections`). A settings file (`agent.json`, `extensions.json`, `prompt-suggestions.json`, `permissions.json`) is decided by ONE `ConfigurationReviewCallout` at the top of its page (`ProjectCapabilityTrustNotice` for `agent.json`, user and project); its trusted state shows as a quiet line with **Revoke** only on the page that owns it (General with the project column on, Extensions, Suggestions, Permission rules). A waiting user permission file or `agent.json` says "the last version you trusted stays in effect".
- **Untrusted project file:** no per-row lock icons. The project label carries ONE lock (tooltip "Not applied until you review <name>'s settings file"); the project column's switches, radios and controls are disabled and muted, show User's value and stay centered.
- **`LayerSwitches`:** two switches per row, User then project, emitting `onChange(layer, value)`; callers apply the semantics (a project value equal to User's means follow again). Project-defined items have no User switch: the slot stays empty at the same width, no dash. `pending` hides the switches; `locked` (project file not trusted) shows a disabled, muted project switch with User's value. Switches never get a ↺.
- **Table alignment (`LayerCells`):** layered lists read as tables. Every layer column is one fixed, equal-width cell (`w-24`) and BOTH its label and its control (switch, radio) are centered in it, so they line up exactly (the label line pads for the card's 1px border); the trailing chevron/actions column keeps its width under the labels too. `ColumnLabels`, `LayerSwitches` and radio cells all render through `LayerCells`, so the widths are the same in every group and on every table of a page. A radio table (extension accounts) uses the same cells.
- **Title rows stay simple (`LayerEnabledTable`):** a detail page's title row holds at most ONE simple action (New profile, Reload, a single enable switch without a project). Anything more goes below the description: the User/project enable switches become an "Enabled" (or "Available") one-row card right under the page header, with no section heading and the labels on a short right-aligned line above it (extension, sub-agent launch and suggestion pages); icon actions (Duplicate, Open file, Review trust, Revert, Delete) become a row of small outline `Button`s with icon and label.
- **`LayerRow` + `SplitColumns`:** value settings with wide controls: label and description full width, then the User and project controls in two equal halves, with the labels on their own line above the section's card (`SettingsSection` `splitLabels`). Each half is [control][↺ slot], so the halves stay equal and the ↺ sits inside its own half. Without the project column the row is the single-control row. The ↺ (`reset`) belongs to value cells only.
- **General and Tools are User-only by default:** the one-column layout. With a project open the page header has a labelled switch "Project overrides" (`ProjectColumnsToggle`) with a brand count badge of the settings the project changes on that page (hidden at 0), tooltip "Show this project's values next to yours. …". Turning it on adds the project column (General: the `LayerRow` halves; Tools: the list table). The choice is remembered per page in the client's UI state (`features/settings/state/project-columns`), not in settings. While the column is hidden, a row the project overrides shows a small brand briefcase right after its title (`ProjectOverrideMark`, tooltip "Overridden in this project"; `LayerRow` `overriddenIn`, a `PageItem` badge). Without a project there is no switch and no marker. An untrusted file keeps the callout; counts and markers still show.
- **Empty columns:** a layer that does not exist or does not apply leaves its cell empty (or a muted `projectNote`), so columns stay aligned.
- **`LevelMenu`:** an action that targets a layer. A plain button without a project; a User / project-name dropdown with one.
- **`TipBadge`, `HoverTip`:** a badge or small target that explains itself on hover.

Page actions (New …, Reload) go in the page header right of the title through the shell's `pageActions` snippet, as small outline buttons with icon and label. Lists with at least 20 items (`SETTINGS_SEARCH_MIN`) get a search field, never full width: `SearchInput` with `class="max-w-xs"`, the same on every page (Skills, Tools, Profiles, Accounts, Suggestions, Shortcuts). Nav count badges are small solid warning circles (16px, `SettingsNav`).

## Profiles, suggestions and rule sets

- **Agents / Sub-Agents:** list → detail. Groups Project → User → Built-in; a row shows a summary of the profile's changes ("Permissions Read only · Plan review On · 1 more change", or "Uses your defaults"), badges (Both, Replaces built-in, Replaced by the project copy), Duplicate, and, on Sub-Agents only, the launch `LayerSwitches` (`subagents.<name>.enabled`). A user or project profile changed outside Nerve waits for review as a problem line with **Review** (the review dialog); its page has the review callout, **Review** for a trusted one, and What it can do and Source at the end; a declined one shows the Declined badge. A waiting profile is also listed, disabled, in the composer's profile picker (with **Review** in its footer) and in `/profile` (Needs review; Enter shows **Review**). **New profile** is a header `LevelMenu` that creates and opens the profile.
- **Profile detail:** a Profile section (label, read-only ID, when to use, used as), then Changes. Changes start empty; **Add a change** offers every setting grouped Basics / Tools / Skills and only what is added is stored. A change row shows its value as the status line, a Required / Recommended `TipBadge`, a lock that switches the mode, and remove; the row opens its editor. Built-in profiles are read-only with **Customize** (`LevelMenu`), which saves a copy with the same ID that replaces them. Sub-Agents put the launch switches in the header under the column labels.
- **Suggestions:** Project → User → Built-in groups with `LayerSwitches` per layer (a project-defined suggestion has no User switch), a badge (No JS, or the decision state of the whole file) with a tooltip, and a "Waiting for your review" problem line with **Review** that hides the switches; the suggestion's page has the review callout and What it can do and Source. The project's enablement file (`.nerve/config/prompt-suggestions.json`) is trusted by exact content like the other project settings files: while it needs review or is declined it is ignored and the project column is locked (one lock on its label) under the file's callout, which decides it inline; edits made in the app keep it trusted. **New suggestion** is a header `LevelMenu`.
- **Permission rules:** User and Built-in groups without switches (rule sets are chosen in General). The Default badge says where to change it; project overlays are a count in the row's summary. A user rule set changed outside Nerve shows "Waiting for your review" with **Review** on its row, and its page has the review callout and What it can do and Source. The user's and the project's `permissions.json` are decided by the file callouts on the list (the project's also in each rule set's Project overrides section).

## Sections are surfaces

`SettingsSection` draws its body as a bordered `card` (`rounded-lg`) with the heading outside, above it; the surface, not a rule, separates sections. Pass `divided` for rows: the body becomes `divide-y divide-border` with no padding and `FieldRow` pads itself (`min-h-12 px-3 py-2`). From the `@md/page` container width rows use a fixed 14rem control column, so controls align across rows and sections; narrower panes stack.

Put controls directly in the row's `control` snippet: Select, Input with suffix, Switch; do not pair a value with a "Change" button. Nested cards read the `data-page-surface` contract and sit flush (`PageList`, `PageEmptyState variant="card"`, the model catalog). Group related controls into few sections.

## Lists

Entity lists and catalogs (tools, skills, extensions, providers, accounts) are a single `PageList` (bordered `card` surface, hairline-divided rows) holding `PageItem` rows, never a stack of individually tinted cards. The anatomy is fixed:

- **Left:** an identity icon tile (or a custom mark such as a provider logo), then the title with badges for exceptional states only (Experimental, Default, Shadowed, a version), and one status line under it.
- **Selectable rows:** a list that chooses one of its items (the account an extension uses) puts a radio (`select` snippet of `PageItem`, inside a ui-kit `RadioGroup`) in the icon's slot. The row keeps everything else: it still opens the item, and its actions stay. `iconLabel` adds a kind tooltip to an icon tile (Features rows).
- **Status line:** the summary of how the item is set up, or what it does when it has no settings. A problem replaces it in warning tone, followed by its fix action, so every row keeps its height. Never write "Off" there; the switch says it.
- **Right:** change indicator and other quiet meta, icon actions (entity lists), lock, then the switch or "Always on", then a chevron when the row opens something.
- **Opening:** the whole row opens the item's detail view or dialog. Never add a per-row Configure or Edit button; the row is that button. Lists that open nothing keep the chevron slot empty so switches align.
- **Compact:** `compact` makes a single-line row (`min-h-10`, no status line); use it for reference lists whose rows never have a second line (shortcuts).
- **Off:** the title and icon turn muted; the row stays readable and openable.

Row actions are `IconAction`s, which require a label and supply the tooltip and accessible name; keep them to actions other than opening (Test, Copy, Delete). Detail editing belongs in a dialog or detail view, not inline on the page.

### List → inner page

Anything with more to show than a row (an extension, a permission rule set, a prompt suggestion) opens an **inner page**, never an in-place expansion: the row is a plain `PageItem` with a chevron and its summary on the status line. A page opts in by declaring `detail` in the registry (`settings-page-data.ts`); the shell then tracks the open item, restores the list's scroll on back, and Escape returns to the list. The page renders its own `PageHeader` with `parent` set, so the title becomes a breadcrumb (`Permission rules › Name`) in the same box as the list header, with the item's description and its page actions (an enable switch) in the actions slot; nothing moves vertically and the heading takes focus on open. The detail's body is ordinary `SettingsSection`s. A list that has nothing more to show (storage categories) opens nothing. Compact lists without identity (shortcuts, devices, activity) use `PageItem` without an icon.

### Skill review

Settings › Skills lists user and project skills with their decision: a skill that waits shows "Waiting for your review" or "Changed since you trusted it" as its problem line with **Review** (the review dialog), and no switch; a declined one shows the Declined badge. A project skill, and a user skill with a decision, opens an inner page (`SkillReviewPage`, `detail` item `user:<name>` or `project:<name>`): the review callout, then What it can do and Source (the files the decision covers, scripts marked, each opening in a file tab; `SKILL.md` is not inlined). Built-in skills have no review UI. Rules: [trust](../architecture/trust.md).

## Review dialog

`ConfigurationReviewDialog` (`$lib/presentation/configuration-review`) is the one review for every kind, rendered once by `ConfigurationReviewHost` and opened anywhere with `openConfigurationReview(targets, startIndex)` (`$lib/application/configuration-review`). It reads `configuration.review` and decides with `configuration.decide` on the digest it showed.

- **Header:** kind icon, `Trust "name"?`, the `TrustStateBadge`, "kind · User/Project", and with several items "2 of 4" with Previous and Next; ✕ closes the whole queue.
- **Body:** "Changed outside Nerve's settings · 2 min ago" (or "Added …") while it waits; **What it can do** (`ReviewCapabilityList`: broad items first with a warning icon, a `New` badge for what was not approved before, `code` spans as inline code); **Source** (`ReviewSourceList`: mono paths with **Open** in Nerve's file viewer, scripts marked Script); "Trust covers this exact version. A change outside Nerve asks again." No embedded source, no raw JSON, no digests.
- **Footer:** **Details** (the item's Settings page) on the left; **Not now** (next item, closes after the last), **Decline**, **Trust**; a trusted item offers **Revoke**. Each decision moves to the next item. If the item changed while it was open, the dialog shows the new review with a warning instead of deciding.
- **Phone:** the same dialog; Details and Open are hidden.

## Accounts

Accounts are added, edited and chosen on the page of the extension that uses them; **Models and accounts › Accounts** is only an index of them. Never link from an extension page to the index to manage accounts.

- **Extension page:** the account section lists the accounts of the extension's kind with a radio that chooses the one the extension uses. With a project open each row has two radio slots under quiet column labels, User and the project: the project follows User until it picks another account, and picking User's account again clears the override (no ↺ on radios). Project accounts have no User radio. The header has an outline **Add account** button (Plus icon), repeated as the action of the empty state. Opening a row edits the account; a problem line offers **Sign in** (`needs_sign_in`, kinds with a provider) or **Retry** (last test failed), otherwise **Edit**.
- **Adding:** the dialog is generated from the kind's manifest, with the typed-in secrets. With a project open it asks "Available to": User or "Project only"; an extension defined by the project can only add project accounts, so the level is pinned. A kind that signs in submits as **Add and sign in** (otherwise **Add**) and the same dialog then shows the sign-in interaction (`AccountSignInPanel`, the shared interaction panel also used by the Providers page) and closes when it succeeds. Only this app can start, answer or cancel a sign-in.
- **Accounts page:** an index, no Add account. Accounts sit in `OriginGroup`s (`layers={false}`): the open project first, then User. A row shows the account name, the extension and a detail summary, a problem line with its **Sign in** or **Retry** action, a health icon that tests the account, a menu (Sign in again, Move to user/project level, Duplicate to a level, Clear credentials) and Delete. Moves and duplicates offer only the levels the kind allows; a project-defined kind's accounts stay in their project. Duplicating a signed-in account warns that both copies share one sign-in. Opening a row navigates to the owning extension's page. The search ("N of M") appears from 20 accounts and matches the name, kind, platform, defining extension, level and state. The empty state reads "No accounts" / "Add an account from the page of the extension that uses it."

## Remote connections

**System › Remote connections** (owned by the access feature) is how phones and other computers reach Nerve, simplest first. **Anywhere, with Tailscale**: one Private access switch; while it starts or has a problem, one status line with the fix (a link, a command to copy, Try again); once ready, a card with a pairing QR code (a fresh five-minute, single-use code for the Tailscale address, so one scan opens and pairs), the setup steps and the address to copy. The port select shows only while the switch is on. **On the same network**: Allow devices on this network, then HTTPS for phones and its port only when they apply, with Pair a device in the header. Bind host and HTTP port stay on **System › System** (Listener). Paired devices are managed on **Devices**.

## Background jobs

**System › Background jobs** lists the daemon's periodic work as one `PageList`: each `PageItem` has the job's label and description, a "Running" or "Failing" badge, a problem line with the last error while it fails, and one muted line with the last run (when, and its summary) and the next run. The only action is an `IconAction` **Run now**, disabled while the job runs. Jobs have no switch; credential refresh is not optional, because turning it off only makes sign-ins expire. A job that keeps failing, and an account that needs sign-in, also reach the Activity bell as notices that link to this page or to Accounts. Design: [background jobs](../architecture/background-jobs.md).

## Storage

**System › Storage** opens on the daemon's last scan (kept in memory until a forced refresh or a cleanup), so the page shows numbers at once; a scan older than a minute is redone in the background while the summary says "Updating". The summary is the total, the Nerve home and "Updated 2 min ago" with a **Measure again** icon action, and one bar: the four largest categories in colour, the rest in one neutral segment. **What uses space** lists categories largest first with the same colour dots, size and share on the right, a lock for protected data, and **Free up space** on cleanable rows, which opens the cleanup dialog with only that item selected (the header's outline **Clean up** opens it with the recommended set). Categories under 1% fold behind "Show N smaller items". **Largest conversations** rows open the conversation. A cleanup is ONE `Callout` at the top: `info` with a spinner, count, progress and **Stop** while it runs, then `success`, `warning` or `destructive` with what it freed and **Dismiss**. A failed scan shows a warning in the summary line when older numbers are shown, else an empty state with **Try again**. Only deleting conversations asks for a second confirmation.

## MCP servers

**Agent › MCP servers** is one layered page that takes the open project, laid out like Extensions. Servers sit in `OriginGroup`s (Project, then User) with the layered **Enabled** switches of Skills; a project server has no User switch, and the project column is locked while the project's `agent.json` is untrusted. A row is an extension row: icon tile, name, one status line (the reason it is not working, else where it comes from ("From your settings", "Replaces yours", "Replaced in project"), the tool count and the description or command), the switches and the chevron. No state badge except Declined, and no row menu: a waiting entry's problem line has **Review**, and everything else is on the server's page. **Add server** is a header action; the dialog is a form (stdio command, arguments, environment, working directory, or HTTP URL and headers) or **Paste JSON** (an `mcpServers` snippet or one entry), and saving opens the new server's page.

A row opens the server's inner page (`McpServerDetailPage`, `detail` item `server`, id `<scope>:<name>` because a project server and a user server can share a name). The header is `MCP servers › [plug] name` with the description or command, and the enable switch (with a project open, the **Enabled** `LayerEnabledTable` under the header). An entry waiting for review shows the review callout (**Decline** · **Trust**; a declined one a quiet callout with **Trust**), then **What it can do** from the shared review, read-only: saving through Nerve records approval, so a waiting entry is not editable until approved. An approved entry shows **Tools** (tool names as chips, each description in a tooltip; the server name and version and resource count as the description; **Test again** and, while connected, **Disconnect**), tested on open while the server is on and again after each save; then the entry edited in place: **Server** (name, Local command or HTTP URL, command, arguments one per line, working directory, or URL; description; request timeout) and **Environment** or **Headers**. Edits save when focus leaves the editor, on Enter, on removing a row or switching Secret, and when the page closes; a validation problem shows as a callout and nothing is saved. A renamed server's page follows the new name. Each environment or header value can be marked **Secret**: it goes to the credential vault and the file keeps a `${secret:<name>}` reference; a stored secret is never shown and a blank field keeps it. A file that is invalid on disk is not overwritten until the user chooses **Replace with a valid file**. **Source** closes the page: where it is defined (the file, with **Open file** for a project entry), the trust with **Revoke**, and **Remove server**. Trust opens the review dialog; Decline and Revoke decide on the exact entry the page read. A row's **Review** opens the review dialog. Design: [configuration](../architecture/configuration.md).

## Entity cards

`EntityCard` is one card per entity: header (title, then badges, actions on the right), muted description, `EntityRow` changes divided by hairlines (muted label column, foreground value, icon actions), ghost `Button size="sm"` footer. Never put `well` behind editable rows: `well` is for recessed output.

## Provenance

Show provenance only when it differs. A setting that matches where it would otherwise come from shows nothing: no per-row source badges. One that differs (a user value that differs from the built-in default, a project value that differs from the user's, a conversation value that differs from its profile) gets `SettingsChangeIndicator`: a single ↺ that marks the change and resets it, with the inherited value in its tooltip ("Reset to default (Balanced)"). It goes in the row's `badges` slot, or `meta` for a `PageItem`. There is no page-level summary or bulk reset in the header: the project column shows the differences, each one resets in its own cell, and on General and Tools the overrides switch's badge counts them. Fixed values say who fixed them in a tooltip ("Locked by Planning"), not a disabled-looking input.

## Model choice

`ModelPicker` (`$lib/presentation/model-picker`) chooses ONE model together with its reasoning level, constrained to the levels that model supports; use it wherever a single model is chosen (settings, profile changes, tool config, composer). `ModelMultiSelect` chooses several (the model scope). They are not interchangeable.
