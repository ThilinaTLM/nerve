# Extension platform

An **extension** is a unit of capability with its own settings, accounts and permissions. It contributes `quick_script` namespaces and optionally direct tools. The built-ins (Atlassian, Web, Diagrams, Image generation, Image explanation) are written against `@nervekit/extension-api` and run in-process, except Diagrams, which runs in a sandbox; the host knows none of them by name. The API itself (types, fields, `ctx` services) is documented in the doc comments of [`packages/extension-api/src/types.ts`](../../packages/extension-api/src/types.ts) and not repeated here; this page owns the design rules and the security rules the host enforces on it. The runtime and permission model are in [code mode](code-mode.md) and [permissions](permissions.md), settings and accounts storage in [configuration](configuration.md#extension-settings), and packages in [codebase](codebase.md).

The API is built to be isolated: an extension's code can run in its own sandbox (see [Sandbox adapter](#sandbox-adapter)); Diagrams does today. Extensions can also be installed as folders ([Installed extensions](#installed-extensions)); the SDK and UI contributions are not shipped yet (see [Not shipped](#not-shipped)).

## Rules

1. **Extension code imports only `@nervekit/extension-api`** (built-ins, which are host code) **or `@nervekit/extension-sdk`** (installed extensions; the SDK build rejects a direct API import) and its own files. No host objects, no `fetch`, no file system. _Why:_ this is what keeps the contract publishable and sandbox-ready. The boundary checker enforces the dependency, and the [`extension-naming` rule](../../scripts/checks/extension-naming-policy.ts) forbids every other production source from naming an extension; only the built-in list and frozen migration steps do. Its exception list is reviewed and may only shrink; rule sets select extension operations by risk (`external_read`), not by namespace.
2. **Every `ctx` call is async and exchanges plain data** (JSON values, `Uint8Array`, handles); no class instances or callbacks cross. Where a callback would decide something, an option states it: `http.request` takes `response: "artifact"` with `artifact: { name?, baseName?, extension?, inlineText? }` (the host names the file and derives the extension from the content type), and `models.vision.explain` reports deltas only through its named `progress` sections. `ctx.signal` stays for in-process code; sandboxed code cannot hold a signal, and the host cancels its invocation natively, so new code must not depend on it. _Why:_ a later `__hostCall` transport must work without an API change.
3. **The extension declares; the host decides.** Permissions, approvals, network policy and limits are host code. The manifest is plain data except its hooks (`test`, `availability`, `parse`, `authorize`, `run`); contracts validate the data part, typed against the API.
4. **`parse` and `authorize` are synchronous and pure**, so authorization happens before any I/O. `authorize` returns one check, several (all must pass) or none. Extension authors write them as plain synchronous functions; the _host_ calls them through the asynchronous `ExtensionCode` interface ([`code-adapter.ts`](../../packages/tools/src/extension-host/code-adapter.ts)): `parse`, `authorize`, `resource`, `run`, `present`, `configuration`, `availability`, `testAccount` and `dispose`, all returning promises and exchanging plain data. `SdkMethod.prepare` is therefore asynchronous too, but it still completes (parse, authorize, resource) before any I/O of the call and before approval. The in-process adapter runs definitions in the host; the [sandbox adapter](#sandbox-adapter) implements the same interface over a persistent runtime. The runtime opens an extension's code on the first call into it during a run and disposes it when the run ends (`ExtensionRuntime.dispose`).
5. **Account kinds are unique across extensions** (built-ins and user extensions share one namespace; a project extension's kinds are unique within its project); the registry rejects duplicates. Their fields cannot be `account` or `model` (the account dialog has no control for them), so such a kind fails registration. A kind is an _account definition_; several definitions may share a **platform** name ([Platforms and uses](#platforms-and-uses)).

## Context security

`ctx` is the only way out of extension code ([`ExtensionContext`](../../packages/extension-api/src/types.ts), host side in [`extension-host/`](../../packages/tools/src/extension-host)).

- **Secrets never reach extension code.** `ctx.accounts.selected` returns non-secret fields, the account's `level` and the identity its provider reported (short plain strings), never a credential. `ctx.http` asks the [credential vault](#credential-vault) what the account's credential adds to each hop (a header, or a query parameter) and applies it on the host side; the response comes back, the request headers the host added do not. The backend, the UI frames, the agent, logs and error messages never receive a credential: a provider's errors reach them only as a fixed message ("The <kind> account needs sign-in"). Breaking this makes every extension a credential-exfiltration risk, so a new `ctx` service must never return or echo a secret.
- **Credential origins are checked per hop.** A credential is sent only to the account kind's own `origins` (templated from account fields); for a platform use, only to the origins the extension declared that the definition also covers. Each redirect hop is re-resolved: every header and query parameter a credential added is removed from the hop and added back only if that hop's origin is allowed (a failure of a hop whose URL carried a credential parameter is not repeated in the error). A credential provider's `apply` runs before each hop to an allowed origin, so whatever it sees can only travel to the origin the request was already going to. A 401/403 from a redirect target that got no credential (a signed media URL) is a normal response; only the credentialed origin's 401/403 becomes the host error (`UNAUTHORIZED` ends the run, `FORBIDDEN` names the account and the fix). _Why:_ the extension must not need to know about, or be able to leak, auth headers.
- **The network is an allowlist.** `ctx.http` reaches only origins in the manifest's `permissions.network`. Patterns are URL origins with `*` for one host label, `*` alone for any public http(s) origin (Web fetch; it never carries a credential), or templates over a selected account's field or an extension setting. Templated destinations are user-supplied and may be on a private network; every other origin goes through the SSRF guard on every hop, and redirects are manual and capped.
- **Uploads stream from the host.** A multipart part with `data: { handle }` is read and streamed by the host from the authorized artifact or workspace file, so large bytes never enter extension code. `ctx.artifacts.read` has a smaller limit than transfers; limits live in code.
- **Files are authorized, not ambient.** A method reaches a workspace file only through a handle its `authorize` declared as a host-tool check (such as `read`); an undeclared read fails with `DENIED`. Extension code has no file-system access, and its docs are declared as paths the host reads.
- **`ctx.authorize` has a risk ceiling.** It runs the same nested authorization as declared checks, is bound to the running call, and is refused with `BAD_REQUEST` before any approval when its risk is above the method's declared `risk`. It is unavailable outside a call. This is the same invariant as the executor's declared-risk guard in [code mode](code-mode.md#permissions), and the script scan depends on it.
- **`riskFromArgs`.** A method whose risk depends on argument values (a raw `request`: GET is external_read, anything else destructive) declares `riskFromArgs: true`. The script scan then needs literal arguments and takes the risk from the method's own `authorize`; with a computed verb the script counts as destructive and is not admissible by operation rules. The scanner names no extension.
- **Approval target.** The approval of a quick_script or extension tool covers the resolved extension settings and, per enabled extension, each selected account's id, kind, name and non-secret fields. Switching an account's site must end approvals.
- **Errors.** Extensions throw `ExtensionError(code, message, { fix })` from a closed code set; the host formats it for the agent. A failing account `test` hook reports a reason (`rejected`, `restricted`, `unavailable`, `unreachable`) so Settings can word it.

## Availability and accounts

- Availability is **derived** from the manifest: the extension's switch and the namespace's `enabledBy` (one setting or any of a list), then `requires` (the selected account exists and is `ready`), then the optional `availability(ctx)` hook. Reasons and fixes are generated with the extension's name, so there are no per-extension texts. Details in [code mode](code-mode.md#configuration).
- The Extensions page reads the manifest's `contributes` from the extension metadata: each namespace with its optional `label` (the id when absent), and each direct tool as `{ name, label, description }` (`label` defaults to the name).
- **Accounts are generic** and described in [Accounts](#accounts): stored in the `account` table ([storage](storage.md#accounts)), user- or project-level, credentials in the vault. `requires` is met by a selected account whose state is `ready`; one that needs sign-in makes the extension unavailable with a fix that says so (`needs_sign_in`, `failed` and `unavailable` each have their own reason and fix). Availability never refreshes: an account with a refresh token is `ready` even when its access token has expired. Account ids are local to a home, so a project file naming an account this user lacks leaves the extension unavailable with a fix naming the extension page; it never falls back to another account. Default project and space keys stay on the Atlassian account, because a key is meaningful only on its site.
- The Settings Accounts page, account dialog and "Test" button are generated from the manifest; no app code names a product.

## Accounts

An **account** is a credential an extension's requests use, and the user adds, signs in to and manages it in Settings ([Accounts page](../ui/settings.md#accounts)). The extension never sees the credential; the host owns storage, refresh, sign-in UI, consent and origin checks for every mechanism. Standard mechanisms are declared as data and run by the host; anything else is the extension's own **credential provider**, code that runs in a separate sandbox.

```mermaid

  subgraph Extension
    B["Backend sandbox<br/>(no credentials)"]
    C["Credential sandbox<br/>(sees credentials, no free I/O)"]
  end
  subgraph Host
    H["ctx.http"]
    V["Credential vault<br/>store · refresh · state"]
    S["Sign-in service<br/>interactions · redirects"]
  end
  B -- "request + account" --> H
  H -- "apply(request)" --> C
  C -- "headers / query" --> H
  H -- "signed hop, allowed origin only" --> N["Service"]
  N -- "response" --> H --> B
  S <-- "signIn / refresh" --> C
  C <--> V
```

### Account kinds and providers

An account kind (`AccountKindData`, doc comments in [`settings.ts`](../../packages/extension-api/src/settings.ts)) declares non-secret `fields`, typed-in secrets (`secret` for one, `secrets` by name for several), how `ctx.http` sends them (`auth`: one injection or a list of `basic`, `bearer`, `header`, `query`, each naming the secret it uses), the `origins` the credential may be sent to and a **provider**. All providers implement the same host interface ([`credential-provider.ts`](../../packages/workbench-server/src/domains/accounts/credential-provider.ts)), so the vault, sign-in service, consent and `ctx.http` do not care which one runs:

| Operation                        | Called when                                                   | Returns                                         |
| -------------------------------- | ------------------------------------------------------------- | ----------------------------------------------- |
| `signIn(account, ui)`            | The user clicks Sign in, or saves the account form            | A credential state (opaque JSON) and its expiry |
| `refresh(account, state)`        | Before expiry, or once after a 401 from a credentialed origin | A new state, or "needs sign-in"                 |
| `apply(account, state, request)` | Every `ctx.http` hop to an allowed credential origin          | Headers to set and query parameters to add      |
| `revoke(account, state)`         | The account is deleted (best effort)                          | Nothing                                         |

None is reachable from the backend, UI or agent. The providers:

- **`static`** (no `provider`): the typed-in secrets with the declared injections. Existing manifests keep their meaning. Secrets are inputs, entered in the account dialog and stored in the credential blob.
- **`oauth2`** (`provider: { type: "oauth2", … }`): standard OAuth 2.0, run by the host ([`oauth2-provider.ts`](../../packages/workbench-server/src/domains/accounts/oauth2-provider.ts)). Authorization code with PKCE (a loopback redirect, relayed for a remote browser) and device code; endpoints as URLs, `{<field>}` templates over account fields, or OIDC `discovery`; `scopes`; an optional `userinfo` endpoint that maps JSON paths to identity fields; an optional `revocationUrl` (RFC 7009, called on delete). The access token is sent as `Authorization: Bearer`, so no `auth` is declared. The client id is an **account field** the author may give a default (`clientIdField`, default `clientId`); a client secret, when the service needs one, is an account secret (`clientSecret`). Nerve registers and ships no OAuth apps, so a user can always bring their own. New built-ins are added only for open standards many extensions need, never for one vendor.
- **`extension`** (`provider: "extension"`): the extension's own credential provider, see [Credential sandbox](#credential-sandbox). It lists `signInOrigins`, the origins its own requests may reach.

An account belongs to exactly one definition for its whole life, and its credential is only ever given to that definition's provider.

### Levels

An account has a **level**: a **user-level account** is available in every project, a **project-level account** in one project only. Both live in the Nerve home, never in the repository. A project sees its own accounts and the user accounts. Which levels a kind allows depends on where it is defined:

| Kind defined by                | User-level accounts | Project-level accounts             |
| ------------------------------ | ------------------- | ---------------------------------- |
| Built-in or user extension     | Yes                 | Yes                                |
| Project (repository) extension | No                  | Yes, for the defining project only |

_Why:_ kind names are unique only within one composition (built-ins, user, the current project; [`extension-catalog.ts`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/extension-catalog.ts)), so two repositories can define the same kind with different origins and different credential code; a user-wide account of such a kind would reach whichever repository asks. [`account-levels.ts`](../../packages/workbench-server/src/domains/accounts/account-levels.ts) enforces the rule (`ACCOUNT_LEVEL_NOT_ALLOWED`).

- **Selecting.** An `account` setting saved at user scope selects user-level accounts only; at project or conversation scope it selects user accounts and that project's accounts. Moving an account to a project makes user-scope settings that selected it unresolved, shown with a fix like any missing account.
- **Moving and duplicating** between levels keep the credential, within the table above. A copy shares the original's sign-in: when the service rotates refresh tokens, the first of the two to refresh invalidates the other's token, and that one becomes `needs_sign_in`. The Accounts page warns when duplicating a signed-in account and offers Clear credentials on any account.

### Platforms and uses

Three names let several extensions describe the same kind of account without taking each other's accounts:

- **Platform:** a shared, non-unique name for what the account is for (`github`, `jira`), `AccountKindData.platform`.
- **Account definition:** one extension's description of how to hold an account for a platform; its id is the account kind.
- **Account:** belongs to exactly one definition.

An extension that wants to use accounts rather than define them declares `uses: [{ platform, scopes?, origins? }]`, and its `account` setting names `platform` instead of `kind`. The setting offers every account of that platform whose definition covers the use ([`kindsForUse`](../../packages/contracts/src/domains/extensions/platforms.ts)): the definition's `origins` cover the use's `origins` (absent: the definition's own), and, when the use asks for scopes, the definition has an `oauth2` provider. A use can narrow access, never widen it, and the credential is sent only to the use's origins. Two extensions that both define a GitHub account keep both definitions and their own accounts; the user sees every GitHub account, whichever extension defined it.

- **Scope union.** Scopes requested at sign-in are the union of the definition's and those of every _enabled_ extension that uses its platform, evaluated for the account's level ([`platform-uses.ts`](../../packages/workbench-server/src/domains/accounts/platform-uses.ts)). Granted scopes are stored with the credential. When the union grows (a definition update, a newly enabled user), the affected accounts derive `needs_sign_in` at once, and availability names what is missing.
- **Definition removed or off:** its accounts stay listed with state `unavailable`, naming the extension, and are not offered until it returns; the user can delete them.
- **Consent** is per using extension and platform ([trust](trust.md#extension-grants)).

### Credential vault

[`CredentialVault`](../../packages/workbench-server/src/domains/accounts/credential-vault.ts) is the only reader and writer of the `account.credential` column ([storage](storage.md#accounts)) and the only caller of provider operations; `AccountsService` is the host's account API on top of it. State as the app and availability see it:

- **Stored** in `status`: `ready`, `needs_sign_in` (no credential, refresh refused, cleared) and `failed` (with the provider's message for the user).
- **Derived** when read, never stored: `unavailable` (the definition is gone or off), and `needs_sign_in` because granted scopes are fewer than the union, the access token expired without a refresh token, or the credential was written by credential code that consent no longer covers.

Refresh is the same flow for `oauth2` and extension providers; the vault owns timing, concurrency, persistence and failure handling:

```mermaid
sequenceDiagram
  participant B as Backend (ctx.http)
  participant V as Vault
  participant P as Provider
  participant T as Token endpoint
  participant S as Service
  B->>V: credential for account
  alt expires within 60 s
    V->>P: refresh(state)
    P->>T: grant_type=refresh_token
    T-->>P: access (+ new refresh)
    P-->>V: new state
    V->>V: write row, then use
  end
  V->>P: apply(request)
  P-->>V: headers
  V->>S: request
  S-->>V: 401
  V->>P: refresh once, apply, retry once
```

- **Ahead of expiry, in the background.** The account credential refresh [background job](background-jobs.md#account-credential-refresh) refreshes accounts that expire within 10 minutes and were used in the last 30 days. Accounts not used for 30 days are skipped and become `needs_sign_in` when next used.
- **On use, as the fallback.** For when the daemon was not running or the machine slept: before a credentialed request the vault refreshes when the access token expires within 60 seconds, and once more after a 401 from a credentialed origin, retrying the hop once (streamed bodies are reopened per attempt). A second 401 is the account's error.
- **Single-flight.** One operation per account at a time, whether started by a request or the background job; others wait. One daemon runs per home, so an in-process lock is enough.
- **Last use** (`last_used_at`) is set by credentialed requests and account tests, not by the background refresh, or nothing would ever age out.
- **Rotation.** A new refresh token is written to the row before the new access token is used; a response without one keeps the old.
- **Failures.** `invalid_grant` and `invalid_client` make the account `needs_sign_in` or `failed`, with a fix naming the Accounts page. Network errors and 5xx are transient: the row is unchanged and the request fails as `unreachable`. Extension providers report the same distinction by returning `{ needsSignIn: true }` or throwing.
- **Scopes.** If a refresh grants fewer scopes than the union, the account is `needs_sign_in`.
- **Binding to code.** Credential code that consent no longer covers is not handed the stored credential (the blob records `codeHash`); the account is `needs_sign_in`.

### Sign-in service

[`SignInService`](../../packages/workbench-server/src/domains/auth/sign-in-service.ts) (formerly `OAuthFlowManager`) is the one sign-in flow for model providers and extension accounts. It owns the interaction contract (browser link, device code, choice, text input, progress; `oauthInteractionSchema` in [contracts](../../packages/contracts/src/domains/auth/auth.ts)), the loopback listeners ([`loopback-listener.ts`](../../packages/workbench-server/src/domains/auth/loopback-listener.ts)), the [relay](../../packages/workbench-server/src/domains/auth/oauth-loopback-relay.ts) for a remote browser, timeouts and cancellation; one flow per provider or account at a time. Model providers keep their credentials and provider-specific logic in `pi-ai`'s store and share only the service. Only the app starts, answers or cancels a sign-in; no agent tool, `quick_script` namespace or extension API reaches it ([trust](trust.md)). The app renders it with one shared interaction panel on the Accounts and Providers pages, and the same flow works on the desktop and on a hosted daemon.

### Credential sandbox

An extension provider is built by the SDK from a separate entry (`src/credentials.ts`, `defineCredentialProvider`) into `dist/credentials.js`; the manifest records its SHA-256 and operations (`credentials`). [`credential-sandbox.ts`](../../packages/tools/src/extension-host/credential-sandbox.ts) runs it.

- **Its own sandbox.** A QuickJS runtime separate from the backend's, opened per operation and disposed after it; no memory, session or module state is shared with the backend or between operations, and the backend cannot call the provider. Each operation has its own limits (64 MiB; `signIn` 10 minutes and 500 host calls, `refresh` 60 s, `revoke` 30 s, `apply` 5 s and 50 host calls).
- **Its `ctx` is small and fixed** ([`credentials.ts`](../../packages/extension-api/src/credentials.ts)): `account` (id, kind, fields), `secrets`, `state`, `crypto`, and per operation:
  - `crypto` (all operations): `hash`, `hmac`, `randomBytes` and `sign` (RS/PS/ES/EdDSA for JWT assertions), host-implemented because QuickJS has none.
  - `http` (`signIn`, `refresh`, `revoke`): only to the kind's **sign-in origins**, through the SSRF guard, redirects not followed, 1 MiB responses, 30 s. Responses go back to the provider only.
  - `ui` (`signIn` only): show a link, show a device code, ask a choice, ask for text, show progress, get a loopback redirect URL and wait for its callback; mapped to the sign-in service's interactions.
  - `request` (`apply` only) and **no network**: this is what makes body access safe, since whatever `apply` sees can only travel to the origin the request was already going to.
  - Nothing else: no artifacts, files, settings, extension store, `ctx.authorize`, reports or logs.
- **Output.** `apply` can only add headers and query parameters; it cannot change the method, URL, path or body, so it cannot redirect a request. `signIn` and `refresh` return opaque `state`, an optional expiry and granted scopes, which go to the vault, and optional **identity** fields, which the backend sees as `AccountInfo.identity` after the host checks they are short plain strings.
- **Libraries, not host features.** Signing schemes such as SigV4 or OAuth 1.0a are libraries an author bundles into `credentials.js`; the host provides only the primitives. The SDK's `examples/aws-sigv4` and `examples/github-app` show two.

| Channel          | Rule                                                                                                                                                                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Return values    | `apply` output goes on the wire only for hops to the account's credential origins; the backend sees the response, never the request headers added. `signIn`/`refresh` state goes to the vault. Identity fields are checked (at most 16 entries, 200 characters each) and shown in consent. |
| Network          | Provider `http` reaches only declared sign-in origins; `apply` output reaches only credential origins. Both lists are grants.                                                                                                                                                              |
| Errors and logs  | Provider errors are shown to the user in Settings and reach the backend and agent only as a fixed message. The provider has no log channel.                                                                                                                                                |
| Shared state     | None between the two sandboxes.                                                                                                                                                                                                                                                            |
| Other projects   | A project-defined kind's accounts and credential state are visible only in that project ([Levels](#levels)).                                                                                                                                                                               |
| Echoing services | A service that echoes request headers in its response can leak what `apply` added. The same is true of injected headers; origins are consented and user-templated. Accepted residual risk, called out in consent for broad origins.                                                        |

**Body access.** Signing schemes differ in what they need from the body, so `apply` gets the body on demand: `body.digest(algorithm)` (SHA-256, SHA-384, SHA-512, SHA-1 or MD5; any size, computed once per algorithm by the host, including bodies streamed from files) and `body.bytes()` (buffered bodies up to 20 MiB; otherwise a clear error). That covers every scheme for buffered bodies and every hash-based scheme for any body; only raw-body schemes on large streamed uploads fail.

### Public surface of accounts

Additive: `AccountKindData` gains `platform`, `secrets`, `auth` as a list, the `query` scheme, `provider` (`oauth2` data or `"extension"`) and `signInOrigins`; `ExtensionDefinition.uses`; an `account` setting may name a `platform`; `AccountInfo` gains `level` and `identity`; the new `credentials` surface (`defineCredentialProvider` and its `ctx` types) has its own compatibility floor. `ctx.http` is unchanged for the backend. See [`UPGRADING.md`](../../packages/extension-sdk/UPGRADING.md).

## Direct tools

A manifest can contribute tools (`defineTool`) for work the agent does often enough that discovery through `sdk.*` is too costly; `web_search` (extension `web-search`) is the case. A tool is usually bound to a namespace method, so it shares `parse`, `authorize`, the operation and one implementation (`parse` receives the tool's arguments object as its single argument; a script passes positional arguments). A tool without `method` declares its own `parse`, `authorize` and `run`, and an optional `present` that splits the result into agent text and transcript sections (see [Tool views](#tool-views)).

- A tool is offered only while its extension and switch are on and its `requires` are met; unavailable tools are left out of the request.
- Permission rules match the operation (`search.web`) through `quick_script` operation rules. Exceptions accept core tool names only; one naming an extension tool is rejected with a hint to use `tool: "quick_script"` and the operation.
- `web_fetch` stays a core tool; `web.fetch` is a built-in runtime namespace (not an extension) authorized as `web_fetch`, so URL rules and approvals are unchanged whichever route is used.
- Web search goes through a provider interface ([`providers/`](../../packages/extensions/src/web-search/providers/)): the selected account's kind picks the provider (Tavily first), which normalises results to `{ title, url, content, published? }` plus an optional answer. A provider is an account kind (credential, origins, optional `test`) and a `search` function; its origins are the extension's only network permissions. The `searchAccount` field accepts several kinds as providers are added.

### Tool views

A direct tool describes how it looks with a declarative `view` (`ToolView`, fields in [`types.ts`](../../packages/extension-api/src/types.ts)), not UI code. _Why:_ extension code stays free of UI and sandbox-ready, and the app renders every view with its own primitives across all states (drafting, approval, running, completed, failed, cancelled). The shell owns approval, errors and cancel, so an extension cannot restyle or hide them.

- The default view is one `text` section `result`; `present(output)` splits the result into agent text (keep it complete) and transcript sections (keep them compact).
- The registry validates views when it is built: argument names must be tool parameters, section ids are lowercase and unique, `live` is allowed only on sections that can stream, and `present` may only fill declared sections. A violation fails registry creation with the extension id.

The agent result policy follows the view: with a `links` section the result is projected like the core search tool (item-aware, `details.results` holds the displayed items); otherwise it uses the prose projection ([tool-result projection](tool-result-projection.md)).

`ctx.progress(section, chunk)` streams text into a live section of the running direct tool. Outside a running direct tool, or for a section that is not live, the call is ignored with a warning. The host transports it as the `stream` of the `tool_progress` live delta. Adding a section type means a renderer, a projection rule and a contract change, so it needs a reason an existing type cannot meet.

### Vision capability

`ctx.models.vision` is the host capability behind the Image explanation extension (`explain_image`):

- `explain` returns the explanation text and streams thinking and answer chunks into the live sections the caller names; `ready()` reports whether a usable model is configured, so `availability` can hide the tool with a fix (signatures in [`types.ts`](../../packages/extension-api/src/types.ts)).
- The host reads the model and thinking level from the calling extension's own `model` (capability `vision`) and `thinkingLevel` settings. Callers cannot pick a model, so an extension cannot spend credit on, or send images to, a model the user did not choose for it.
- The host detects JPEG, PNG, GIF and WebP from the bytes. The file is read under the `read` rules its `authorize` declared.

## Sandbox adapter

[`sandbox-adapter.ts`](../../packages/tools/src/extension-host/sandbox-adapter.ts) runs an extension's code in a persistent QuickJS runtime, one per extension per run, opened lazily on the first operation and disposed with the run (`ExtensionRuntime.dispose`). The registry's `extensionCodeAdapter` picks the adapter per extension (`routedExtensionCode`); the host composes it from the built-in list's `sandboxedBuiltinExtensions`, so only Diagrams runs sandboxed today. Host code outside that list still never names an extension.

- **Bundle and runtime library.** The extension is built (`scripts/build/copy-extension-assets.ts`, from its `bundle.ts`) into one IIFE classic script that sets `globalThis.__nerveExtension`. It does not contain `@nervekit/extension-api`: the [runtime library](../../packages/tools/src/extension-host/sandbox-runtime/extension-runtime.ts), evaluated first, provides it as `globalThis.__nerveExtensionApi`, so extension and runtime share one `ExtensionError`. The library also supplies `TextEncoder`/`TextDecoder` (QuickJS has none), removes `host` from the globals (only the library can reach the host) and serves the single global `__nerveExtensionInvoke`.
- **Every `ctx` service is a host call.** The sandbox `ctx` forwards to `host.call` with the invocation's token; the host answers from the real `ctx` it builds for that call (same http allowlist, credentials, artifact checks and `ctx.authorize` ceiling as in-process), through a fixed table of methods; anything else is refused. `settings.get` reads a snapshot sent with each invocation. `progress`, `report.*` and `log.*` are fire-and-forget host calls that do not count against the budget and are delivered before the invocation settles.
- **Wire format.** JSON, with bytes as `{ $nerve: "bytes", base64 }` in both directions; handles and `ArtifactRef` are plain data. An `ExtensionError` (code, message, `fix`) crosses unchanged in both directions, so the script sees the same `e.code` and message as in-process; other host failures keep their tool-error code, other extension failures arrive as plain errors with their message.
- **Sessions** live in the runtime for the run. The `ctx` handed to `session` belongs to the call that opened it; a session keeps plain data, not `ctx`.
- **Cancellation** is the native cancel of the runtime's invocations when the run's signal aborts; `ctx.signal` in the sandbox never aborts. Each invocation has its own time and host-call limits.

## Other decisions

- **Extension-owned conversions stay in the extension.** Confluence storage-format conversion is Atlassian code. Plain HTML to Markdown is a host utility (`ctx.text.htmlToMarkdown`, run in the tools worker with time and size limits), because one shared implementation is simpler than a second one and is sandbox-friendly.
- **Docs are declared, not read.** A topic's `file` is relative to the extension's folder and read by the host through `readExtensionAsset`, from source or `dist/extension-assets/`.
- **The icon is a lucide name or a file.** `icon` is one of the allowed lucide names or a relative `.svg` path read through the same `readExtensionAsset`. At registry creation the host checks it (at most 16 KB, square `viewBox`, no script, event attributes, `foreignObject`, `image` or non-`#id` references) and fails with the extension id; the manifest holds the resolved `{ type: "lucide", name }` or `{ type: "svg", src }` (a `data:image/svg+xml` URI), which `extensionMetadata` projects as is. The app renders it as an `<img>`.
- **The registry has no default.** The host composes it from the built-in list, the user's installed extensions and the conversation's project (see [Installed extensions](#installed-extensions)) and passes it to every consumer; the executor throws without one. `@nervekit/extensions` exports the definitions list only, and conversion to the registry form is host code in `tools`.
- **Tests that compose the runtime with built-ins live in the server** (`packages/workbench-server/test/extensions/`), because neither package may import the other. `extension-api/testing` provides a fake `ctx` for unit tests next to extension code.
- **Image backends stay in the host**; the extension asks through the declared `models.image` capability. A call option that does not depend on settings is validated in `parse`, so a bad call never reaches an approval.
- **Settings UI is generated** from the manifest schema (field types, `visibleWhen`, `advanced`, inherited value shown read-only where a field is not settable in the scope). The field set stays small: add a type only when a built-in needs it, because each needs a control, validator and provenance display. Arbitrary JSON Schema is not accepted.

## Installed extensions

The primary use is a user building extensions for themselves by conversation; sharing is secondary. Compatibility is therefore designed to break rarely, break only the affected surface and never silently, and the host keeps no adapters or upgrade-on-read for older extensions.

An installed extension is a folder `<root>/<id>/` whose `dist/` holds `manifest.json` and `backend.js`. Only `dist/` is read. This section covers loading, trust and consent; the SDK, UI contributions and the `configure-nerve` skill are described below and in the SDK's README.

- **Format.** `manifest.json` is the plain-data part of the definition (`extensionDefinitionData` in `@nervekit/extension-api/host`: every hook becomes `true`, so the data says which hooks exist) plus `version` and `sdkVersion`, and a `ui` object (built UI contributions, see [UI contributions](#ui-contributions)). The schema is `installedExtensionManifestSchema` in [contracts](../../packages/contracts/src/domains/extensions/installed-manifest.ts): every object is strict, so an unknown field is a diagnostic with its path. Installed extensions cannot declare `prelude` or settings `migrations`. `backend.js` is a classic script in the same IIFE format as the Diagrams bundle: it registers its definition on `globalThis.__nerveExtension` and takes `@nervekit/extension-api` from `globalThis.__nerveExtensionApi`.
- **Folder name = id.** The id follows the skill naming rule (lowercase letters, digits, single hyphens, at most 64) and starts with a letter. Discovery lists the entries of a root that its `.gitignore`, `.ignore` and `.fdignore` do not ignore (the same reader as skills, `listUnignoredEntries`; dot folders and `node_modules` are skipped).
- **Roots and precedence.** `<project>/.nerve/extensions/` (the project root only, no ancestor walk), then `<NERVE_HOME>/agent/extensions/`, then the built-ins. The first id wins; a shadowed entry stays in the catalog with state `shadowed`. A user or project extension with a built-in id is `invalid`. Account kinds, namespace ids and direct tool names are unique across all scopes, and namespace ids may not take a runtime namespace or a host global; the later one fails with a diagnostic. "Later" means built-ins, then user, then project, so a repository's extension can never take an account kind (and the credentials stored under it) from one the user already has. Project-extension themes (`ui.themes`) are ignored with a warning.
- **Load path.** Read `manifest.json` (no code runs), check the folder name, SDK range, icon and doc topics (read through `dist/` with containment checks; icons get the checks of [`icon.ts`](../../packages/tools/src/extension-host/icon.ts)), ask the trust gate, and only if it says `trusted` open `backend.js` in a throwaway sandbox runtime (`readSandboxedDefinitionData`, the runtime library's `describe` operation) and compare the data of the definition it registers with `manifest.json`. Any difference refuses the extension and names the first differing path. Installed extensions always run through the sandbox adapter: the catalog's `sandboxed` check is true for every installed definition.
- **Compatibility.** `oldestCompatibleSdkVersion` ([contracts](../../packages/contracts/src/domains/extensions/compatibility.ts)) holds one floor per surface: `manifest`, `backend`, `ui` (bridge and `ui-kit`), `credentials` and `themes`; a floor is raised only by a release that breaks that surface, with an `UPGRADING.md` section. `sdkVersion` stays the one recorded value, and `apiVersion` no longer exists. `readFolder` reads `sdkVersion` leniently **before** the strict manifest schema and checks it against the floors of the surfaces the manifest uses (`usedExtensionSurfaces`: backend with namespaces, tools or accounts; ui with previews, pages or panels; themes with themes). A version below a floor or above the running Nerve gives state `incompatible` with a message naming the surface and the SDK version that changed it (an unparsed manifest from a newer SDK is `incompatible`, never `invalid`); only a compatible version is parsed. The user is told to ask the agent to upgrade it with the configure-nerve skill. [`public-surface.test.ts`](../../packages/extension-sdk/test/public-surface.test.ts) compares the emitted declarations of the API and SDK entries, the bridge method table and the manifest and theme JSON Schemas with a committed snapshot, so a change to any of them is a decision (additive, or raise a floor and add a section).
- **Trust gate.** [`ExtensionTrustGate`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/trust-gate.ts) is consulted before an installed extension enters any registry and before its code is opened: `trusted` or `pending` (with the consent to review). The host's gate is [`ExtensionConsentRepository`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/extension-consent.ts), which keeps one `extension` row per folder in `trusted_resource` ([trust](trust.md)); without a consent store nothing installed runs, and tests pass `overrideTrustGate()` or an in-memory store. Revoking keeps the row as `rejected`, and a rejected extension is pending review again. There is no environment override.
- **Trust records.** One `trusted_resource` row of kind `extension` per installed extension ([trust](trust.md)): `project_id` for a project extension (`NULL` for a user one), `resource_key` the folder, `name` the id, `content_digest` the `dist/` hash (relative path and bytes of every file, sorted; `manifest.json` is in it) and `grants` the grant snapshot (network origins including account credential origins, capabilities, account kinds, credential providers with their sign-in origins, scopes and credential code hash, platform uses, namespaces with their operations, direct tools, UI contributions). Rules: nothing runs before consent; a project extension is pending again on any content change; a user extension keeps consent through a code-only change and is pending again when its grants gain anything (the review lists only what is new); removed grants need no consent, and the stored snapshot narrows so that adding one back asks again; revoking keeps the row as `rejected`. The on/off switch is not part of consent: a consented installed extension uses the same settings `enabled` value as a built-in (user, project and conversation scopes, `config/extensions.json`); consent only decides whether the extension is loaded at all.
- **Consent summary.** [`consent-summary.ts`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/consent-summary.ts) builds `ExtensionCatalogEntry.consent` from the manifest: structured items (`kind`, `text`, `broad`) plus a text form ("Connects to api.github.com", "Uses your GitHub account (account kind github)", "Signs in to your GitHub account with OAuth 2.0 and keeps it signed in", "Runs its own code with your AWS credentials", "Uses your github accounts with scopes repo", "Adds agent tools: x, y", "Adds SDK namespace z (operations a, b)", "Uses a vision model", `*` network called out as broad access). Its `contentHash` is what a consent must name, so a consent only ever covers the files that were shown.
- **Consent operations.** `extensions.grantConsent`, `extensions.revokeConsent` and `extensions.reload` are workbench protocol methods of the signed-in app connection, implemented by `ExtensionCatalog` (`ExtensionManagement`). No tool, `quick_script` namespace or extension port exposes them (a test pins this). Each ends in `reload(id)`, which publishes `extensions.changed`.
- **Agent-facing text.** [`agent-text-limits.ts`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/agent-text-limits.ts) holds the limits: namespace summary, each rule, method description, doc topic (`whenToRead` and file) and direct tool description are checked when the folder is read, and an extension over a limit is `invalid` with the limit in its diagnostics; error messages (and their fix) from installed code are cut at run time. Namespaces of installed extensions are attributed (`csv-tools, user extension`) in the `quick_script` description, `sdk.list` and `sdk.docs`; built-ins are unchanged.
- **Registry per scope.** [`ExtensionCatalog`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/extension-catalog.ts) composes built-ins, the user's extensions (scanned once, shared) and the project's, per project directory. `registryFor(projectDir)` is what the `quick_script` description, the direct tools, `sdk.list`/availability, the permission scan and the account kinds read. There are no file watchers: `reload()` (all) or `reload(id)` re-reads, consults the gate again (a reload never grants consent) and applies to the next request that asks for a registry. Direct tools of installed extensions are published to a per-project tool scope (`setScopedToolDefinitions`, keyed by project directory) when their registry is composed, and withdrawn on reload; tool lookups for execution, argument checks, permission requests and result projection take the project (`toolDefinitionByName(name, projectDir)`), so two projects with the same extension id and different definitions never see each other's. The global tool catalog holds only core and built-in tools.
- **Agent loop.** `extensions.reload(id)` and `extensions.status(id)` in `quick_script` ([code-mode](code-mode.md)) call `ExtensionCatalog.agentPort(project)`: reload re-reads one folder in the conversation's project and returns the status; status reports state, source, folder, consent (`pending`, `granted`, `not_required`, `unknown`), the extension's switch, diagnostics and `recentErrors`. They never grant or revoke consent and expose neither the content hash nor the consent text. Errors come from [`ExtensionErrorLog`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/extension-errors.ts), fed by `limitInstalledErrors` (every hook of installed code, including `host.call` from frames; 20 per extension, cleared on reload). Frame console errors are not collected.
- **Catalog.** `ExtensionsView.catalog` (extensions API) lists every extension known at the target, built-in, user and the project's, with `state` (`enabled`, `pending_consent`, `incompatible`, `invalid`, `shadowed`), `source`, folder path and diagnostics; `ExtensionMetadata.source` is `builtin`, `user` or `project`.
- **SDK.** [`@nervekit/extension-sdk`](../../packages/extension-sdk/README.md) (with `extension-api` and `ui-kit`, published manually in lockstep with Nerve's version) produces this format: `nerve-ext build` bundles `src/extension.ts` into the `backend.js` IIFE (extension-api mapped to `globalThis.__nerveExtensionApi`), evaluates the definition in a `node:vm` context, and writes `manifest.json` from `extensionDefinitionData` plus `version` and `sdkVersion`, validated with `installedExtensionManifestSchema` (inlined into the SDK build; contracts stays private). The built-in [`configure-nerve` skill](../../packages/workbench-server/src/builtin-skills/builtin/configure-nerve/guide/extensions.md) drives it: `scripts/create-extension.mjs` runs `npx --package @nervekit/extension-sdk@<Nerve version> nerve-ext init`, installs and runs `check`; `scripts/upgrade-extension.mjs` bumps the SDK and prints the `UPGRADING.md` sections in between; `scripts/install-extension.mjs` installs and builds a folder the agent did not scaffold, after `--list` has printed its dependencies for the user. Every script installs with `--ignore-scripts` (the lockfile when the folder has one: `npm ci`, `pnpm install --frozen-lockfile`) and prints the dependencies other than the SDK packages first. The version comes from `scripts/nerve-version.json`, which `scripts/build/copy-skills-assets.ts` writes into the copied skill from the root `package.json` (so dist and the desktop bundle carry it), or, in a source checkout, from the root `package.json` found above the script. `NERVE_EXTENSION_SDK_SPEC` replaces the published SDK with any npm spec; the scripts then install it into a temporary folder instead of using `npx`. Dev slots (`pnpm dev`, `pnpm desktop:dev`) set it to `file:<repo>/packages/extension-sdk` unless it is already set (`developmentEnvironment`), and their builds include the SDK, so extension work on a dev slot uses this checkout's SDK: npm links the folder and the SDK's own dependencies resolve through the workspace. `desktop:prod` and packaged builds never set it. To test the published package form instead, point it at packed tarballs and set `NERVE_EXTENSION_NPM_OVERRIDES` (JSON, package to spec) for the unpublished `extension-api` and `ui-kit`, as `pnpm --filter @nervekit/extension-sdk e2e` does. The skill ships no hand-written API reference. At build time `scripts/build/copy-skills-assets.ts` copies the declarations of `extension-api` and `extension-sdk` into the skill's `reference/extensions/api/` and generates `reference/schemas/` from the contracts' zod schemas, so the doc comments in those packages are the agent's API reference; `packages/extension-sdk/test/skill.test.ts` builds the two `examples/` projects with the SDK and covers the scripts' helpers, and the server's skill catalog test pins the agent text limits. `packages/workbench-server/test/extensions/installed/sdk-fixture` is a prebuilt SDK output that the host's reader and loader are tested against; the SDK's tests keep it current.

### Public surface and frozen names

- **Author surface.** `extension-api/src/index.ts` is a hand-written export list; the SDK re-exports it, and installed extensions import only the SDK. Names for the host (`EXTENSION_ERROR_CODES`, `isMethodTool`, `parseOptions`, `extensionDefinitionData`, the image backend request types) are in the `@nervekit/extension-api/host` entry, which the skill's API reference does not ship. Public types name no provider: `ImageOptions.backend` is a string the host validates.
- **Host-owned prefixes.** An installed extension's tool names start with its id with hyphens as underscores plus `_` (`csv-viewer` → `csv_viewer_`), and its account kinds start with its id. `installedNamingDiagnostics` ([installed-naming.ts](../../packages/contracts/src/domains/extensions/installed-naming.ts)) states the required prefix in a `tool-name-prefix` or `account-kind-prefix` diagnostic; the SDK build and `readFolder` both run it, so the author learns at build time and a hand-edited manifest is `invalid`. Built-ins are exempt.
- **Frozen names (contract).** These are part of every built extension and of the frame; renaming or reshaping one breaks every installed extension and needs a raised floor ([Installed extensions](#installed-extensions)): the bundle global `globalThis.__nerveExtension` (the registered definition), `globalThis.__nerveExtensionApi` (the API object the bundle reads, whose members are the public index), `globalThis.__nerveExtensionInvoke(payload, invocationId)` (the host's single entry into the runtime), and the frame bridge's `postMessage` envelope (`nerveBridge: 1`, `type`, `bridgeProtocolVersion`, the method table in `bridgeMethods`; see [Bridge](#ui-contributions)).

### Builds and sharing

- **Nerve never builds or installs.** No code path of the daemon, the catalog or `extensions.reload` runs `npm`, `pnpm` or `nerve-ext`; reload and the catalog read `dist/` only (checked: the only spawn of those tools is in the SDK's own CLI and the skill's scripts, which run as agent commands in a conversation the user started, under the permission engine). Not after an update, not at consent, not on reload.
- **Shared as source.** The scaffold's `.gitignore` lists `dist/`, `node_modules/` and `.nerve-ext/`. A folder with sources and no `dist/` reports `not-built` ("ask the agent to build it"); the consent then covers the output built on the receiver's machine.
- **Dependencies are the risk in a received folder.** Before installing in a folder it did not scaffold, the agent runs `install-extension.mjs --list`, shows the dependency list to the user and waits. A dependency's code still runs during the build and the tests, outside the sandbox.

## UI contributions

The contracts for previews, pages, panels and themes (step 5a). The server, app and SDK implement against these schemas.

- **Authoring.** `ui?: ExtensionUi` on the definition (`PreviewContribution`, `PageContribution`, `PanelContribution`, `ThemeContribution` in `@nervekit/extension-api`). `entry` and `file` are source paths the SDK build compiles or copies. `extensionDefinitionData` leaves `ui` out, so the sandbox-versus-manifest comparison does not see source paths.
- **Manifest.** `installedExtensionUiSchema` ([installed-manifest.ts](../../packages/contracts/src/domains/extensions/installed-manifest.ts)) is the built output, strict: previews `{ id, label, match: { extensions }, edit, entry }`, pages `{ id, label, icon, newMenu, entry }`, panels `{ id, label, icon, entry }`, themes `{ id, label, kind, file }`. Ids are kebab-case and unique per kind (`uiContributionIdSchema`); at most `extensionUiLimits.maxPerKind` per kind. Output paths are fixed: `uiEntryPath(id)` is `ui/<id>/index.html`, `themeFilePath(id)` is `themes/<id>.json`. `newMenu` (default `true`: list the page in the new-tab menu, the chevron next to +; not a grant) is resolved the same way. `edit` is always resolved in the manifest: the SDK applies `defaultPreviewEdit(extensions)` (`none` when every extension is a known binary format, otherwise `source`).
- **Consent.** A UI contribution is a grant. [`consent-summary.ts`](../../packages/workbench-server/src/core-host/extensions/extension-catalog/consent-summary.ts) snapshots one entry per previewed file type (`previews:<id>:<ext>`), `previews-edit:<id>` for `edit: "custom"` (called out as broad), `pages:<id>`, `panels:<id>` and `themes:<id>`, and words them as "Opens .csv, .tsv files as "Table"", "Adds a page …", "Adds a side panel …", "Adds the color theme …". An update lists only what was added.
- **Theme files.** `themeFileSchema` ([theme-file.ts](../../packages/contracts/src/domains/extensions/theme-file.ts)): `{ id, label, kind, tokens }` with the `requiredThemeTokens` (the eight colour inputs and nine syntax roles every theme block of `theme.css` sets) and nothing outside `themeTokenNames`. A token added later is listed in `optionalThemeTokens` with a default derived from the required ones (`themeTokenDefaults`), so a theme written earlier stays valid: the schema output always holds every token, an unknown token is an error. Colours are `themeColorSchema`: hex or an `rgb`/`hsl`/`hwb`/`lab`/`lch`/`oklab`/`oklch` function with plain numbers; no `url()`, `var()`, `calc()` or nested functions. The `--step-*` and `--mix-*` tuning tokens some built-ins override (`themeTuningTokens`) are not settable by extensions. `test/extensions/theme-file.test.ts` fails when `theme.css` gains or loses a per-theme token. `themeTokensCss` renders the declarations.
- **Theme ids.** `colorThemeSchema` is a built-in id (`builtInColorThemeSchema`) or `ext:<extension-id>/<theme-id>` (`extensionColorThemeId`, `parseExtensionColorTheme`). `colorThemeKind` stays the built-in table; `resolveColorThemeKind(theme, lookup?)` answers for any theme, with extension kinds supplied at runtime and `nerve-dark`'s kind when the theme is not loaded.
- **Bridge.** [ui-bridge.ts](../../packages/contracts/src/domains/extensions/ui-bridge.ts) defines the `postMessage` protocol, version `bridgeProtocolVersion`. Envelopes carry `nerveBridge: 1` and a `type`: `ready` (frame to host, asks for `init`), `frameError` (frame to host, no response: an uncaught error, unhandled rejection or CSP violation, recorded for `extensions.status().recentErrors` as `frame:<kind>/<id>`; the host dedupes and caps it at `maxFrameErrorsPerLoad`), `init` (`bridgeInitSchema`: contribution kind, id and edit mode, extension id, mode, theme kind, token CSS, base CSS URL, page params), `request`, `response` (`ok` with `result`, or `error { code, message }`) and `event`. `bridgeMethods` holds the params and result schema of every method, `bridgeMethodKinds` the contribution kinds that may call it (`file.*` previews only; `file.write` and `mode.get` only previews with `edit: "custom"`, see `isBridgeMethodAllowed`), `bridgeEvents` the event payloads (`themeChanged`, `fileChanged`, `modeChanged`, `extensionStoreChanged`). `clipboard.*` is answered by the app only while the frame's click is a transient user activation (it propagates to the embedding page). `extensionStore.*` reaches the daemon, which keeps one JSON file per key under `<data>/extension-store/<extension-id>/<project-id>/` with a `revision`; writes with a stale `ifRevision` fail with `conflict`, and every write publishes `extensions.store.changed` (with the writing frame's `origin`, so it skips its own change). The backend's `ctx.extensionStore` uses the same store. Hosts call `validateBridgeRequest(request, contribution)` for every request. Limits are in `bridgeLimits` (message size, read chunk, write size, view state, call args).

### UI contributions: server side (step 5b)

The daemon serves frames and answers the bridge requests that need it; the app owns the rest of the bridge (see the app side once it lands). Code: [`core-host/extensions/extension-ui/`](../../packages/workbench-server/src/core-host/extensions/extension-ui/) and [`extension-frame-routes.ts`](../../packages/workbench-server/src/adapters/http/routes/extension-frame-routes.ts).

- **What is served.** The catalog lists, per project, the loaded installed extensions that have a `ui` section (`installedUi(projectDir)`: consented, valid, not shadowed; user extensions in every project, project extensions in their own). A frame is also served only while the settings switch (`enabled`, resolved at the project) is on. Pending, disabled, invalid and other projects' extensions answer 404.
- **Frame URLs.** `/ext-frame/<token>/<extensionId>/<contributionId>/<file>`; `index.html` is the entry. `<token>` is 32 random bytes (hex) per project, created on first use and kept for the daemon's lifetime, so a frame URL of one project cannot be derived from another's. Like `/html-preview/…` the route is not behind the API credential (a sandboxed frame's requests carry no header); the token is the capability, and request logs show `:token`. Only `extensions.ui.contributions` hands out frame URLs, so the app never builds them. Files come from `dist/ui/<contributionId>/` and must be declared in the manifest.
- **File rules.** Path normalised and contained (symbolic links resolved and refused when they leave the folder, `O_NOFOLLOW`, same file after open), at most 10 MiB, mime allowlist by extension (`html js mjs css json png jpg jpeg gif webp avif bmp ico svg woff woff2 ttf otf`; no `.wasm`, `.map`, `.txt`), `GET` and `HEAD` only. A refusal is a plain 404 that never says why.
- **Headers.** `Content-Security-Policy`: `default-src 'none'; sandbox allow-scripts; base-uri`, `script-src` (the frame folder and `'wasm-unsafe-eval'` for WebAssembly), `style-src` (the frame folder, `/ext-frame/base.css` and `'unsafe-inline'` for libraries that insert `<style>` elements), `img-src` (folder, `data:`, `blob:`), `font-src` (folder, `/ext-frame/assets/`, `data:`), `worker-src` (folder, `blob:`), `media-src blob: data:`, `connect-src 'none'`, `frame-src 'none'`, `object-src 'none'`, `form-action 'none'`, `frame-ancestors 'self'` (only the app's origin may embed), (inline styles are safe because nothing a style can load leaves the allowlists, and `connect-src 'none'` stays). Also `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `Access-Control-Allow-Origin: *` (the frame's origin is opaque, module scripts and fonts load in CORS mode). Sources are written with the request's origin, like the HTML preview. The same code serves the desktop app and a hosted daemon.
- **Base stylesheet.** `/ext-frame/base.css` plus `/ext-frame/assets/<font>` are built by [`scripts/build/build-extension-frame-css.ts`](../../scripts/build/build-extension-frame-css.ts) (part of the workbench-server `build`) from the ui-kit styles with the Tailwind preset: theme structure and derived tokens, base layer, animations, component CSS and fonts, with the per-theme token blocks cut out (their values come from `init.tokensCss`). The output is `packages/workbench-server/dist/ext-frame/`; the desktop bundle copies it to `dist/ext-frame/` and requires `base.css` (`bundle-desktop.ts`). `NERVE_EXT_FRAME_DIST` overrides the folder. Frames need `class="dark"` on `<html>` for dark themes (the SDK's frame client does it from `init.themeKind`).
- **Operations.** [`extension-ui-operations.ts`](../../packages/contracts/src/domains/extensions/extension-ui-operations.ts), addressed to `workbench_server` only, like the consent operations (no agent tool, `quick_script` namespace or extension port reaches them; `consent-flow.test.ts` checks it):
  - `extensions.ui.contributions` `{ projectId }` → `{ baseCssUrl, previews, pages, panels }` with `extensionId`, `extensionName`, `source`, `id`, `label`, `frameUrl`, previews `match.extensions` and `edit`, pages and panels `icon`, pages `newMenu`. The app lists the active project's pages with `newMenu` in the split `+` menu of the tab strip (`newTabMenuGroups`, grouped under the extension name when several extensions contribute). Catalog entries of installed extensions carry `adds` (the full consent summary), shown in the extension's detail under Adds, with Source (folder, versions, consent with Review/Revoke) and diagnostics.
  - `extensions.ui.themes` `{}` → `{ themes: [{ id: "ext:<ext>/<theme>", extensionId, extensionName, label, kind, tokens, tokensCss }] }`: themes of enabled **user** extensions only (a theme is app-wide).
  - `extensions.ui.<method>` for `file.info`, `file.read`, `file.write`, `settings.get`, `project.info`, `call` and `extensionStore.*` (plus `extensions.ui.reportFrameError`): input `{ projectId, extensionId, contribution: { kind, id }, filePath?, params }` (`params` is `bridgeMethods[method].params`), output `bridgeMethods[method].result`. Pure host-UI methods (`ui.*`, `openFile`, `openPage`, `composer.insert`, `viewState.*`, `mode.get`, `clipboard.*`) never reach the server.
  - Failures are `ApplicationError`s with `details.bridgeCode` (a `BridgeErrorCode`); the app answers the frame with that code and the message.
- **Request checks.** Every request is validated again with `validateBridgeRequest` against the contribution as the _manifest_ declares it (kind and `edit`, never the caller's claim), so `file.*` is for previews, `file.write` only for `edit: "custom"`. File methods work on `filePath`, the file of the tab: it must resolve (symbolic links included) to a regular file inside the project and end in one of the preview's declared extensions. `file.read` honours `offset`/`length` and `bridgeLimits`; `file.write` replaces the file atomically (same mode, at most `maxWriteBytes`) and never creates one. `settings.get` returns the resolved values of the extension at the project (settings hold no secrets; credentials live in accounts).
- **Calls from UI.** `call` runs one of the extension's own methods (`namespace.method`, in its own definition) through `callExtensionMethodFromUi` ([`ui-call.ts`](../../packages/tools/src/extension-host/ui-call.ts)), outside any conversation: the sandbox adapter opens the extension's bundle with a `ctx` bound to the open project (settings, accounts, `ctx.http` allowlist and SSRF guard unchanged), and no permission rule or prompt applies. Rules that stay: the method receives `args` as its single argument; reads it declares in `authorize` must resolve inside the project (otherwise `failed`); `ctx.authorize` always succeeds, so it cannot be used to widen anything; a 60 s timeout ends the call and the sandbox; the result must be JSON within the message limit; the backend's error message comes back as `backend_error` (already bounded by the installed-error limits).
- **Themes.** `read-installed.ts` reads each declared theme file when the folder is read (plain data, before any consent): at most 16 KiB, `themeFileSchema`, id and kind equal to the manifest's, and the readability rules of [`theme-rules.ts`](../../packages/contracts/src/domains/extensions/theme-rules.ts): `themeRuleProblems` checks text and syntax contrast against the background, the subdued background, a visible primary, distinguishable syntax roles and a kind that matches the background. `theme-contrast.test.ts` uses the same helpers and holds every built-in theme to `themeRuleProblemsOf`. A theme that fails is not offered and shows as a warning in the extension's catalog diagnostics; it does not make the extension invalid.
- **Reload.** Unchanged: `extensions.reload` and consent changes re-read the folders and emit `extensions.changed`; the next `extensions.ui.contributions`/`themes` call reflects them. Frame tokens survive a reload.

## Change risk

| Change                                             | Risk                                                                                                       |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| New `ctx` service or `http` option                 | Security boundary: must keep secrets host-side and stay serializable. Update the fake context.             |
| Credential injection, origin matching, redirects   | Credential leak. Test each hop.                                                                            |
| Credential sandbox `ctx`, `apply` output, errors   | Credential leak through a new channel. Test per channel (return values, network, errors, logs).            |
| Declared risk, `ctx.authorize`, `riskFromArgs`     | Silent permission widening. The script scan and declared-risk guard depend on them.                        |
| Account kind, account id or credential blob format | Needs a home migration step (the `account` table and `credential` column, [storage](storage.md#accounts)). |
| New view section type                              | Contracts, transcript renderer and projection rule.                                                        |
| Naming an extension outside its folder             | Fails the `extension-naming` rule; derive from the registry instead.                                       |

## Not shipped

The remaining design is tracked in GitHub issues: running the other built-ins in the QuickJS sandbox ([#598](https://github.com/ThilinaTLM/nerve/issues/598)), and the release of installable extensions (publishing the SDK packages, as the [release runbook](../runbooks/release.md) describes). Until the SDK packages are published, extensions build only against a checkout. Not built, and not planned: single-file packages, install from a URL, a marketplace or registry, custom transcript renderers, and compatibility adapters in the host (an extension that no longer fits stops loading and the user upgrades it in a conversation, with `configuration.list({ kind: "extension", state: "incompatible" })` and the bell naming every one). MCP servers are a separate proposal ([#602](https://github.com/ThilinaTLM/nerve/issues/602)).
